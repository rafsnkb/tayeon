### 글자 크기를 목업에서 읽는 법 (2026-09-24에 세 번 틀리고 정리)

**잉크 높이로 재지 말 것.** 안티에일리어싱이 위아래로 2~3px 씩 부풀려서 14px 글자가 18px 로
나온다. 이 방법으로 재서 모달 전체를 한 단계 크게 만들었다.

맞는 방법은 **가로폭**이다:

1. 브라우저에 Pretendard 를 띄우고 그 문자열의 `getBoundingClientRect().width` 를 100px 기준으로
   잰다 → "글자크기 1px 당 가로폭".
2. 목업에서 같은 문자열의 잉크 **가로 범위**를 재서 그 값으로 나눈다.

오차 1% 안쪽으로 떨어진다(예: 모달 바닥 문구 실측 257.7 / 14px 예측 258.9 / 15px 예측 277.5).
한글 글자폭은 굵기마다 다르다 — Pretendard Bold 는 0.92em, SemiBold 는 0.864em, 공백 0.24~0.28em.

### 1. 미수령 리워드 수령 화면 — **로컬에서 끝까지 눌러 봄 (2026-09-24)**

에뮬레이터(Firestore + Auth)에 미수령 리워드를 심고 브라우저로 직접 열었다. 목록 → 조합 선택 →
받기 → 수령완료 → 보유 이용권까지 **전 구간 정상 동작**. 다크·라이트 둘 다 확인.

```
firebase emulators:start --only firestore,auth --project tayeon-test
FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:9099 \
  GCLOUD_PROJECT=tayeon-test GOOGLE_APPLICATION_CREDENTIALS=<더미SA.json> npm run dev
node scripts/dev-seed-pending-rewards.mjs   # 토큰 출력 (같은 환경변수 필요)
# 브라우저 콘솔: await window.__devSignIn("<토큰>")  ← NEXT_PUBLIC_FIREBASE_EMULATORS=1 일 때만
```

- `scripts/dev-seed-pending-rewards.mjs` — 미수령 2건(친구 결제 18회 / 보너스 333회)과 프로필을
  심고 커스텀 토큰을 찍는다. 에뮬레이터 환경변수가 없으면 즉시 중단한다.
- `src/lib/firebase/client.ts` — `NEXT_PUBLIC_FIREBASE_EMULATORS=1` + 비프로덕션일 때만
  에뮬레이터에 붙고 `window.__devSignIn` 을 연다. 카카오 로그인은 실제 콘솔·도메인이 있어야 해서
  로컬에서 로그인 뒤 화면을 볼 방법이 없었다 — 그 구멍을 메운 것이다.
- `firebase.json` 에 `emulators` 블록(auth 9099 / firestore 8080 / ui 4000)을 넣었다.

**⚠️ 로컬에서 브라우저는 `127.0.0.1` 이 아니라 `localhost` 로 열 것.** Next 16 이 dev 리소스의
교차 출처 접근을 막아서, 127.0.0.1 로 열면 클라이언트 번들이 통째로 차단돼 **빈 화면**이 된다
(에러도 안 난다 — 원인 찾는 데 시간을 썼다).

**확인된 숫자** — 친구 결제 18회 리워드(basis 5,400)의 조합별 환산이 규칙과 정확히 맞는다:
타로 전용 18/12/9/7, +사주 15/10/7/5, +자미두수 13/9/6/4, +사주+자미두수 9/6/4/3.

**이번에 눈에 띈 것 (미조치, 판단 필요)**

1. **미선택 라디오가 "채워진 회색 원"이다** — `ComboAllowanceCard.tsx:39`. 선택 상태는 핑크 채움,
   미선택은 회색 채움이라 **둘 다 채워진 원**이고, 특히 라이트에서 미선택이 선택된 것처럼 읽힌다.
   보통은 미선택이 빈 원(테두리만)이다. 카드 테두리가 핑크로 같이 바뀌어서 치명적이진 않다.
2. **자미두수 팝업 제목이 "상품 구매 불가"** — `NoBirthTimePopup.tsx` 를 구매(`/charge`)와
   수령(`/received-passes`)이 공유하는데 제목이 하드코딩이다. 리워드 수령은 구매가 아니다.
3. **클라이언트와 서버의 "태어난 시간 있음" 판정이 다르다** — 화면은
   `birthInfo.birthDate` + `timeUnknown` 만 보고(`RoomsContext`), 서버는 `isValidBirthInfo()` 로
   `gender`/`calendarType`/`jasiRule` 까지 요구한다(claim route). 그 필드들이 없는 오래된 계정이
   있다면 **조합이 선택되고 받기 버튼도 눌리는데 서버가 409** 로 막고, 화면에는 엉뚱하게
   "태어난 시간이 없으면…" 팝업이 뜬다. 실제로 그런 계정이 있는지는 확인 안 했다(시드 데이터로
   이 경로를 재현해 본 것이라, 라이브에 해당 계정이 있는지는 별개 문제다).

**여전히 못 한 것** — 이건 어디까지나 로컬 재현이다. 목업(`MyPass_Send`)이 저장소에 없어서
픽셀 대조는 못 했고, 실계정·실 데이터로는 확인하지 않았다.

하네스는 `FIRESTORE_EMULATOR_HOST` 가 없으면 아무것도 하지 않고 즉시 죽는다 — 실 Firestore 로
잘못 돌리는 사고를 막는다. **그래도 실 Firestore 에서 이 함수들을 직접 호출하지 말 것**:

|---|---:|---:|---:|

| 110,000원 | 10회 | 11회 | 10회 |

`birthdayMMDD` 동등 쿼리라 검증하려면 유저 문서를 날짜에 맞춰 심어야 한다.

## 리딩 스트리밍 전환 + 사주 시간축 + 사주 서비스 설계 (2026-09-26)

### 1. 리딩 응답을 스트리밍으로 바꿨다 — 20~30초 → **첫 글자 1.9초**

켈틱크로스 + 사주 + 자미두수는 출력만 2,700 토큰이라, 다 만들고 나서 주면 20~30초를 빈 화면으로
기다린다. **시간제 이용권은 그 동안에도 시간이 흐른다.**

`/api/tarot/reading` 이 NDJSON 스트림을 낸다.

```
{"t":"cards",...}    ← 즉시. 카드는 LLM 이전에 확정된다
{"t":"delta","v":"…"} ← 약 2초부터
{"t":"redo"}          ← 형식이 깨져 다시 만드는 중(있을 때만)
{"t":"replace","v":"…"} ← 다시 만든 쪽이 온전할 때만
{"t":"done",...}      ← 카드·차감·제안 등 메타데이터
```

**마커가 새지 않게 앞뒤를 쥐고 간다.** 무과금 마커(`[NO_CHARGE]`)는 "응답 맨 첫 글자"로 오도록
프롬프트가 강제하므로 그 길이만큼 모일 때까지 쥐었다가 떼어 내고 흘린다. 꼬리의
`[SUMMARY]`/`[TOPIC]`/`[SUGGESTIONS]` 는 마커 최대 길이만큼 **항상 남겨 둔다** — 마커가 청크
경계에서 잘려도 새어 나가지 않는다.

**사용자가 도중에 나가도 생성·차감·저장은 끝까지 간다.** 쓰기가 실패하면 접고 나머지 일은 계속한다.
그래서 **리딩 락도 백그라운드 작업이 푼다**(`lockHandedOff`) — 응답만 먼저 열고 락을 같이 풀면
아직 생성 중인데 같은 사용자의 다음 요청이 통과한다.

스트림이 열린 뒤엔 HTTP 상태코드를 못 바꾸므로 에러도 `{"t":"error"}` 이벤트로 내려간다. 열리기
**전** 오류(이용권 없음·정지·형식)는 예전처럼 상태코드 + JSON 그대로다.

클라이언트는 델타를 ref 에 모아 **`requestAnimationFrame` 으로 프레임당 한 번만** 화면에 넘긴다.
델타마다 setState 하면 대화 트리 전체가 초당 수십 번 다시 그려진다.

#### 재시도는 "드러내 놓고" 한다

예전엔 카드 누락 등 형식 오류가 나면 조용히 최대 3회까지 다시 만들었다. 스트리밍에선 불가능하다 —
판정에 필요한 `cardsOk`(뽑힌 카드가 답변에 다 나왔는가)는 답변이 끝나야 알 수 있고, 그때는 이미
사용자가 읽고 있다.

그래서 **"빠진 카드가 있어 해석을 다시 정리하고 있어요"** 를 띄우고 한 번 더 만들되,
**다시 만든 쪽이 온전할 때만 교체한다.** 재시도가 더 나빠지면 처음 것을 그대로 둔다 — 멀쩡한 답을
망가진 답으로 바꾸지 않기 위해서다.

### 2. 사주·자미두수에 **시간축**을 넣었다

프롬프트에 이미 *"월운·세운을 근거로 시기를 말할 땐 오늘 날짜 기준으로 판단하라"* 는 지시가 있었는데
**정작 월운·세운을 준 적이 없었다.** 원국(고정된 판)만 넘기고 있었다.

- `src/lib/saju/fortune.ts` (신규) — 대운·세운(작년/올해/내년)·올해 12개월 월운
- `src/lib/ziwei/horoscope.ts` (신규) — 대한·유년·**사화**
- `ziwei/calculate.ts` 는 명반 생성을 `buildAstrolabe` 로 분리(시진·자시 관법 로직이 두 벌 되는 걸 막으려고)

새 알고리즘은 없다. `manseryeok` 의 `luckPillars`, `iztro` 의 `horoscope()` 를 **배선만** 했다.

**시간축은 나에게만 붙인다.** 궁합은 두 사람의 원국을 맞춰 보는 것이지 상대의 운 흐름을 따로 읽는 게
아니고, 양쪽에 붙이면 프롬프트만 두 배가 되면서 모델이 누구의 대운인지 헷갈린다.

실측(Haiku, 켈틱+사주+자미두수, 3회씩):

| | 기존 | 확장 |
|---|---|---|
| 명리 근거가 실린 문장 | 3.7개 | **8.7개** |
| 답변 중 명리 비중 | 7% | **14%** |
| 구체적 시기(N월) 언급 | 1.0종 | **3.0종** |
| 전체 글자수 | 2,336 | 2,436 |
| 원가 | 21.6원 | **22.8원** |

**답변은 안 길어지고 구성만 바뀌었다.** 원가 +1.2원. Sonnet 교체는 하지 않았다(건당 +33원, 3배).

⚠️ **그 대가로 카드가 밀려났다.** "사주·자미두수 각각 최소 세 곳" 만 못 박고 카드 커버리지와의
**우선순위를 안 정해줘서**, 모델이 카드를 깎아 명리 분량을 채웠다. 프롬프트에 *"카드를 한 장도
빠짐없이 다루는 것이 언제나 최우선. 분량이 부담되면 사주·자미두수를 줄여라"* 를 명시해서 닫았다.

### 3. "남은 횟수가 방금 소진됐어요" — 고정 조합 이용권의 구조적 버그

**멀쩡한 이용권을 들고도 모든 요청이 막혔다.** 경로:

```
프롬프트 확장 → 모델 어휘가 "대한·유년·화록" 으로 이동
          → 감지기는 "명궁·신궁·오행국·자미두수" 만 찾음 → 못 찾음
          → ziweiOk=false → ziweiCharged=false
          → 고정 조합(타로+사주+자미두수) 이용권과 조합 불일치
          → availableCount=0 → COUNT_PASS_UNAVAILABLE
```

두 군데를 고쳤다.

1. 감지 목록에 시간축 어휘 추가(대운·세운·월운 / 대한·유년·사화·화록·화권·화과·화기 + 12궁)
2. **근본 원인** — `chargeActiveCountPass` 가 고정 조합 이용권을 **자기 조합으로만** 차감한다

2번이 핵심이다. "모델이 사주를 안 다뤘으면 덜 깎는다"는 설계는 잔량 칸이 조합별로 쪼개진
`combo:"any"` 이용권에서만 의미가 있다. **조합이 하나로 고정된 이용권엔 그런 칸이 없어서**, 덜
깎으려는 시도가 "이 이용권으로는 불가능한 조합"으로 읽혔다. 감지 목록이 답변 어휘를 못 따라가는
일은 앞으로도 생기므로, 그때 요청이 통째로 막히는 대신 정상 차감되게 했다.

### 4. 정지 경고 오탐 — 판단을 서버로 내렸다

*"새 과금 모델을 붙이면 수익이 오를까?"* 같은 정상 질문에 `[NO_CHARGE]`(정지 경고 포함)가 붙는
오탐이 **하루에 두 번** 났다. 프롬프트에 예시와 사고 이력까지 적었는데도 재발했다 — **문구로는
한계다.**

이제 모델이 마커를 붙여도, 질문에 **실제 지시문 신호**(`시스템 프롬프트`, `이전 지시 무시`,
`너는 AI`, `ignore previous`, `jailbreak` …)가 없으면 서버가 **정지 경고를 뗀다**(무과금 안내로 강등).
낮출 때 `[reading] NO_CHARGE 오탐 의심` 으로 로그를 남긴다.

> 판단 근거: **틀렸을 때의 비용이 양쪽에서 크게 다르다.** 잘못된 안내는 성가신 정도지만, 돈 내고
> 쓰는 사람에게 잘못 띄운 정지 경고는 그 사람을 잃는다.

**완전한 해결은 아니다** — 카드는 여전히 안 뽑히고 차감도 안 된다. 거절 자체를 멈추려면 모델을
바꾸거나 분류를 별도 호출로 떼야 한다.

### 5. 화면 — 스크롤·카드·연출

**스크롤을 전면 재작성했다.** 예전엔 맨 끝 sentinel 에 `scrollIntoView({block:"end"})` 하나였는데,
그건 sentinel 의 **아랫변을 스크롤 영역 아랫변에 맞춰서** 컴포저에 가리지 말라고 준 `paddingBottom`
을 화면 밖으로 밀어냈다 — 마지막 말풍선이 이용권 바·입력창 뒤로 들어가던 원인이다.

지금 동작: **질문을 보내면 그 질문이 상단바 바로 아래로 올라가고, 답변은 그 자리에서 아래로 찍힌다.**
스크롤은 더 움직이지 않는다.

- 질문을 맨 위로 올리려면 아래에 한 화면만큼 내용이 필요해서, 대화 끝에 빈 공간을 깔고 답변이 자라는
  만큼 줄인다. 줄이기만 하고 스크롤은 안 건드리니 읽던 자리가 안 흔들린다.
- 상단바는 `absolute h-16` **오버레이**라 스크롤 영역의 0 지점이 바 뒤다. 바 높이를 **재서** 그만큼
  더 내린다(상수로 박으면 바가 바뀔 때 같이 틀어진다).
- 계산은 `useLayoutEffect` — 페인트 **전에** 확정해야 한 프레임 튐이 안 생긴다.
- **기준점은 "가장 최근 질문"이다.** "마지막 메시지가 질문일 때"로 잡으면 답변이 붙는 순간 기준점이
  사라져 "맨 아래로" 예비 경로를 탄다(실제로 냈다 — 읽는 중에 끝으로 끌려갔다).
- 스트리밍 표시를 끄는 건 **`finally` 한 곳**에서만 한다. 중간에 `await refreshMe()` 가 끼면 답변이
  한 프레임 통째로 사라졌다 나타나면서 스크롤이 튄다.

**카드**: LLM 을 기다릴 이유가 없어서 스트림 첫 이벤트로 먼저 깐다. 스프레드 **배열 순서**대로
0.12초씩 밀려 페이드인 한다(DOM 순서가 아니라 카드 인덱스 기준 — 켈틱크로스는 그리드라 둘이 다르다).
켈틱크로스 중앙 칸에 `z-10` 을 줬다: 가로로 눕힌 도전 카드가 제 칸을 넘어가는데 `right`/`down` 이
뒤에 그려지는 형제라 위를 덮고 있었다.

**인사말**에 타이핑 효과를 붙였다(28ms/자). 리딩 본문은 스트리밍 덕에 저절로 타이핑처럼 나오는데
인사말만 한 번에 떠서, 미리 준비된 안내문처럼 읽혔다. 앞 줄을 다 찍고 0.4초 쉬었다가 다음 줄이
시작한다 — 예전의 "말풍선마다 1초 고정"은 줄 길이가 제각각이라 짧은 줄 뒤엔 뜸이, 긴 줄 뒤엔 겹침이
생겼다.

**"새 대화" 버튼이 다시 방을 만든다.** 한동안 방을 안 만들고 메인으로만 보냈는데(빈 방이 쌓이는 걸
막으려고), 그 대가로 **눌러도 아무 일도 안 일어나는** 화면이 됐다. 빈 방 문제는 **이미 있는 빈 방을
재사용**하는 것으로 풀었다 — 열 번 눌러도 빈 방은 하나를 넘지 않는다. 방 개수 상한에 걸리면 조용히
메인으로 보낸다(여기서 상한 모달을 띄우면 "새 대화"를 누른 사람에게 지우기를 강요하는 흐름이 된다).

그 밖에: 타이핑 로딩 문구가 **한 글자만 찍고 멈추던 버그**(`typedLength` 가 의존성에서 빠져 다음
타이머가 안 걸렸다), 이용권 없을 때 바에 "보유 이용권이 없습니다." 표시(겸사겸사 바가 사라졌다
나타나며 컴포저가 40px 튀던 것도 없어졌다), 스프레드 선택을 localStorage 에 고정, 뽑힌 카드 이름
칩 제거 후 `[켈틱크로스][사주][자미두수]` 한 줄로 통일.

### 6. 사주·자미두수 **별도 서비스** 설계 (`doc/사주_구현설계.md`)

`doc/사주구상.md`(GPT 와 짠 콘텐츠 기획, 19개 상품)를 실제로 어떻게 짓는지로 옮겼다. 실측 포함.

- **편당 원가 약 308원** (텍스트 300 + 이미지 8), 첫 페이지까지 42초
- 이미지 `gpt-image-2.5-flare` `1024x1536`/`low` = 158토큰 = **8원**. 세로가 정사각보다 싸고,
  512는 거부되며, `auto` 는 손해다
- **2단 생성**(골격 → 섹션) + 섹션 **순차** + 섹션당 1페이지
- 밟은 함정 5개를 문서에 박아 뒀다: `thinking` 기본 ON(출력 3,000 중 2,955가 thinking), 어미를
  기계적으로 금지하면 해요체가 무너짐, 이미지 브리프가 내담자 본인을 그림, 소제목에 섹션명 그대로,
  Haiku 는 시스템 블록 2,048토큰 미만이면 캐시가 안 걸림

**미해결 중 제일 큰 것**: 순차 생성 147초를 누가 돌리나 → 페이지 단위 온디맨드 + prefetch 안을
적어 뒀지만 아직 구현·검증 전이다.

### 오늘 얻은 것 — 다음에 또 쓸 것

- **"언급했는가"와 "얼마나 했는가"는 다르다.** 프롬프트가 전자만 요구하면 모델은 한 문장으로 요건을
  채운다. 유료 옵션이면 후자를 써야 한다.
- **분량을 요구할 땐 무엇을 희생할지 같이 정해 줘라.** 안 정하면 모델이 알아서 깎는데, 하필 제일
  중요한 것(카드)을 깎는다.
- **감지 목록은 답변 어휘를 못 따라간다.** 프롬프트를 바꾸면 모델 어휘가 움직이고, 그 어휘에 기대던
  검사가 조용히 무너진다. **검사 실패가 서비스 차단으로 이어지는 구조 자체를 없애는 게 낫다.**
- **오탐의 비용은 방향에 따라 다르다.** 안전장치를 걸 땐 "틀리면 어느 쪽이 더 아픈가"로 기울여라.
- **스트리밍은 "기다림"을 없애지 못한다. 옮길 뿐이다.** 총 시간은 그대로고 사용자가 읽는 시간 뒤로
  숨는 것뿐이라, 읽는 속도가 생성 속도를 못 따라잡는 경우에만 통한다.
- **오버레이는 스크롤 좌표계의 0이 아니다.** `absolute` 로 띄운 바/컴포저가 있으면 스크롤 위치
  계산에 그 높이를 반드시 넣어야 한다.
- **문자열 상수가 판정 기준이면 한 곳에 둬라.** `"새 대화"` 가 다섯 군데에 박혀 있었고, 그게
  "아직 안 쓴 방인가" 판정의 기준이었다 → `src/lib/tarot/room.ts` 로 모았다.

## 점검·리팩토링 (2026-09-24 밤)

하루치 작업을 되짚으면서 **입력 휠에서 실제로 잘못된 값이 저장되는 경로 두 개**를 찾아 닫았다.
둘 다 화면에서 굴려 보지 않으면 드러나지 않는 종류라, 계산을 화면 밖으로 꺼내고 테스트를 붙였다.

**1. 윤달이 없는 해에 "음력(윤달)"을 고르면 `"1996--NaN"` 이 저장됐다.**
음력 윤달은 있는 해가 정해져 있다(1996·1997·1999·2000 모두 없다 — 19년에 7번쯤이다). 그런 해를
고르면 월 칸이 **빈 칸**이 되고, 그 상태로 "설정하기"를 누르면 `Number("")` 가 그대로 흘러
`YYYY--NaN` 이 나갔다. 서버도 `if (!body.birthDate)` 로 **빈 값만** 막고 형식은 보지 않아서
그대로 저장되고, 사주 계산과 생일 쿠폰(`birthdayMMDD`)까지 그 값을 받았다.

**2. 모달 안에서 달을 바꿔도 일 칸이 따라오지 않았다.**
칸 목록을 모달 **밖에서** 미리 만들어 넘기고 있어서, 1월 31일에서 2월로 옮겨도 31일이 계속
보였다. 누르면 조용히 28일로 잘렸다 — 사용자가 본 값과 저장된 값이 달랐다.

**고친 방식**

- `WheelPicker` 의 `columns` 를 **함수**(`(draft) => WheelColumn[]`)로 바꿨다. 굴려 놓은 값에서
  칸을 만들기 때문에 달을 옮기면 일 칸이 그 자리에서 줄고, 윤달 없는 해에서 연도를 굴리면 월 칸이
  다시 채워진다. 확정값도 **화면에 보이는 그대로**를 내보낸다.
- 고를 것이 없는 칸이 있으면 "설정하기"가 잠기고 한 줄 안내가 뜬다(`emptyMessage`).
- 날짜 계산을 `src/lib/tarot/birthWheel.ts` 로 꺼냈다(`monthChoices` / `dayCount` /
  `toBirthDate`). `toBirthDate` 는 없는 날짜면 **null** 을 준다 — 만들 수 없을 때 문자열을
  만들어 내지 않는다. 테스트 5개.
- 서버에 형식 검사를 넣었다 — `isBirthDateString`(실재하는 `YYYY-MM-DD`) /

### 휠을 아이폰처럼 원통으로 (2026-09-24, 사용자 요청)

"글자 돌아가는 느낌"을 내려면 **기울이는 것만으로는 안 된다.** 32px 짜리 줄을 18도 눕혀 봐도
거의 표가 나지 않았다(실제로 그렇게 만들어 놓고 눈으로 확인했다). 느낌은 줄이 원통 표면에 있어서
**위아래로 좁혀지는** 데서 나온다.

그래서 줄을 원통 위 제자리로 옮긴다. 각도 θ 인 줄은 중앙에서 `R·sinθ` 떨어져 있고
`R·cosθ - R` 만큼 뒤로 물러나 있다. 흐름상 위치는 `(i - offset)·ROW` 이므로 그 차이를
`translateY` 로 보정하고 `rotateX(-θ)` 를 얹는다. `R = ROW / θ(rad)` — 호 길이가 칸 높이와 맞는
반지름이다. 한 칸당 22도, 원근 420, ±3 칸에서 각도를 멈춘다(더 눕히면 뒤집혀 보인다).

**두 가지를 조심할 것**

- **원근은 줄마다 준다**(`transform: perspective(420px) …`). 스크롤 컨테이너에 `perspective` 를
  걸고 `preserve-3d` 를 이어 붙이는 방법도 크롬에서는 같은 그림이 나오지만, `overflow` 가 있는
  요소는 규격상 3D 문맥이 평면으로 바뀌어서 브라우저마다 보장되지 않는다. 두 방식을 나란히
  띄워 비교했고 결과가 같았다.
- **React 상태로 하지 않는다.** 스크롤은 초당 수십 번이고 연 칸은 줄이 100 개에 가깝다. 보이는
  범위(±4 칸)만 DOM 에 직접 칠하고, 범위를 벗어난 줄은 되돌려 놓는다(안 지우면 화면 밖에 누운
  줄이 남는다).

**스크롤·스냅 기하는 그대로다** — transform 은 레이아웃에 영향을 주지 않으므로 실측 치수
(칸 32, 5 칸, 카드 380×382)와 `scrollTop / ROW` 매핑이 살아 있다. 다만 **보이는 줄 수가 달라
보인다**: 원통이 먼 줄을 안쪽으로 당기기 때문에 위아래로 6~7 번째 줄이 눌린 채 걸친다. 아이폰이
그런 모습이지만 목업(5 칸)과는 다르다 — 원치 않으시면 각도를 낮추면 된다.

기하는 실제 화면 치수로 스크래치 하네스(`.impeccable/wheel3d/`)를 띄워 잡았다. 휠이 있는 화면은
전부 로그인 뒤라 Playwright 로 못 들어간다.

## 뒤로가기 무한 왕복 수정 (2026-09-24)

사용자가 로컬에서 발견: **이용권 구입 → 뒤로가기 → 마이페이지 → 뒤로가기 → 다시 이용권 구입**,
끝없이 반복. 에뮬레이터로 재현해서 히스토리 길이까지 찍어 확인했다.

```
1. 마이페이지        /me                   (history.length=3)
2. 이용권 구입       /charge?from=%2Fme    (4)
3. 뒤로가기          /me                   (5)  ← 줄어야 할 것이 늘었다
4. 뒤로가기          /charge?from=%2Fme    (5)
5. 뒤로가기          /me                   (5)  …
```

**원인** — 2026-09-24에 결제창이 히스토리를 어지럽히는 문제를 고치면서 뒤로가기를
`router.push(from)` 으로 바꿨는데, push 는 히스토리를 **늘린다**. 돌아간 화면(마이페이지)의
뒤로가기는 히스토리 기반(`router.back()`)이라 방금 떠난 구입 화면으로 다시 들어가고, 그 화면이
또 push 하면서 두 화면이 영원히 왕복한다. 두 수정이 서로를 밟은 것이지 어느 한쪽이 틀린 게 아니다.

**고친 방식** — `canReturnByHistory()`(`src/lib/navigation.ts`)가 가른다. `withReturnTo()` 가
모듈 변수에 "어디서 떠났는지"를 적어 두는데, 이 변수는 **같은 문서 안의 화면 전환에서만** 살아
남는다. 결제는 리다이렉트로 돌아오므로 문서가 새로 뜨고 변수가 비어 있다 — 그게 두 경우를
정확히 가르는 신호다.

- 앱 안에서 눌러 들어온 경우 → `router.back()`. 직전 엔트리가 바로 그 화면이라 정확하고,
  히스토리가 줄어든다(왕복이 생길 수 없다).
- 문서가 다시 로드된 경우(결제 후 등) → `router.replace(backHref)`. 히스토리를 믿지 않되
  엔트리를 늘리지도 않는다.

판단을 `SubPageTopBar` 에 뒀다 — `backHref` 를 쓰는 화면이 `/charge` 말고
`/privacy?from=support` 도 있고, 거기도 같은 모양의 왕복이 있었다.

**확인** — 회귀 테스트 4개(`navigation.test.mjs`) + 브라우저 실제 클릭:
구입목록 → 상품선택 → 뒤로(목록) → 뒤로(마이페이지) → 뒤로(메인)까지 history.length 가 4로
고정. 받은 이용권처럼 `backHref` 없는 화면의 기존 동작도 그대로다.

**확인 못 한 것** — 결제를 실제로 거친 뒤의 경로는 로컬에서 결제창을 띄울 수 없어 못 밟아 봤다.
그 경로는 "문서가 다시 로드된다"는 전제 위에 서 있다.

> `prepare` 가 결제창을 열기 전에 **주문 내역**(`paymentIntents/{paymentId}`, 문서 id =
> paymentId)을 적고, `validatePaidPayment` 가 상품표 정가가 아니라 **그 기록과 대조**한다.
> 할인액이 들어갈 자리가 `amountWon` 이다 — 정가는 `listPriceWon` 으로 같이 남긴다.
>
> - 기록이 없으면 **옛 방식(정가 대조)으로 내려간다** — 이 변경 전에 시작된 결제와 옛 코인
>   상품 때문이다. 할인 결제는 `prepare` 가 `await` 로 먼저 쓰므로 반드시 기록이 있고, 따라서
>   **폴백이 할인 구멍이 되지 않는다.**
> - 기록이 있으면 **uid·productId 도 함께 대조**한다. `customData` 는 결국 클라이언트가
>   왕복시키는 값이고 주문 내역은 서버가 적은 값이라, 이쪽이 진실이다 — 예전보다 관문이
>   오히려 촘촘해졌다. uid 불일치에 `autoCancel` 을 켜지 않는 것은 기존 관문과 같은 이유다
>   (남의 결제를 취소시키는 통로가 된다).
> - 결제·이용권 문서의 `priceWon` 이 **실결제액**이 됐다(②와 한 몸). 정가는 `listPriceWon`.
> - 테스트 7 개 추가 (`validatePayment.test.mjs`) — 할인가 통과, 정가 결제 거부, 100 원 결제
>   거부, 기록 없을 때 폴백, uid·상품 위조. 전체 **81 → 88 통과**, `tsc --noEmit` 통과.
>
> 아직 **쿠폰 자체는 없다** — `amountWon` 은 지금 정가와 같은 값이 들어간다. 다음 단계에서
> 쿠폰을 조회해 이 값을 깎는다.

아래는 착수 전에 적어 둔 문제 기술이다(경위로 남긴다).

`src/lib/payment/validatePayment.ts` 가 포트원에서 재조회한 실결제액을 **상품표 정가**와 비교해
다르면 거부한다:

```
if (paidTotal !== product.priceWon || payment.currency !== "KRW")  // 거부
```

`prepare` 는 주문 금액을 **어디에도 저장하지 않는다** — `paymentId` 만 만들어 내려보내고,
기대 금액은 나중에 `productId` 로 상품표에서 다시 꺼낸다. 즉 할인가로 결제하면 **정상 결제가
"금액 불일치"로 거부된다.**

> ⚠️ 그렇다고 이 검사를 느슨하게 풀면 **누구나 100 원을 결제해 11 만원 상품을 받는 구멍**이
> 된다. 반드시 **`prepare` 가 할인 적용된 기대 금액을 서버에 기록하고, 검증이 그 기록과
> 비교**하도록 바꿔야 한다(정가와 비교하는 지금 방식을 대체). 할인액은 **서버가 계산**한다 —
> 클라이언트가 보낸 금액은 절대 믿지 않는다(지금도 `productId` 만 받는다).

**② 리워드 기준 금액이 정가로 기록된다 — ~~감수~~ → 고치기로 했다 (2026-09-25)**

> **뒤집은 이유: 리워드보다 환불 자동승인이 먼저 깨진다.**
> `admin/src/app/api/admin/refund-requests/auto-approve/route.ts:98-99` 가 포트원 실결제액
> (`paidAmount`)과 우리 기록(`recordedAmount = payment.priceWon`)을 대조하고, 다르면
> `assessRefundRisk` 가 사유를 쌓아 `hold: reasons.length > 0`(`refundRisk.ts:73`)로
> **자동 승인을 막는다.** 정가를 계속 기록하면 **쿠폰 구매 건은 환불 요청마다 전부 "금액
> 불일치"로 걸린다** — 돈이 새지는 않지만 운영이 막히고, 쿠폰을 뿌린 뒤에야 드러났을 종류다.
>
> 읽는 쪽을 전수 확인했더니 **정가를 원하는 곳이 하나도 없다** — 환불(실제 낸 돈을 돌려줌),
> 매출 리포트(`functions/src/tawerReport.ts:41` amountField), 사용자 결제 내역, 리워드 3 곳
> (`api/user/bonus-reward/route.ts:34`, `functions/src/index.ts:137`·`:226`) 전부 실결제액이 맞다.
>
> **그래서 `priceWon` 의 의미를 "실결제액"으로 바꾸고, 정가는 `listPriceWon` 새 필드로 남긴다.**
> 필드 이름이 그대로라 **`functions/` 는 한 줄도 고치지 않아도 된다** — `fulfill` 이 실결제액을
>써 넣는 순간 자동으로 실결제액을 합산한다. 과거 문서는 할인이 없어 정가 == 실결제액이라
> 소급 문제도 없다.

아래는 뒤집기 전의 기록이다(판단 경위로 남긴다).

`src/lib/payment/fulfill.ts` 가 결제 문서에 `priceWon: product.priceWon`(정가)를 쓰고, 보너스·
친구 결제 리워드가 이 값을 합산한다. 할인 결제에 정가가 남으면 **실제 받은 돈보다 많은 리워드를
지급한다.**

**사용자 판단(2026-09-24): 큰 문제 아니며 감수한다.** 쿠폰을 자주 뿌릴 계획이 아니고, 런칭
기념으로 30~50% 를 한 번 쓴 뒤로는 5~10% 수준일 것이기 때문이다.

다만 **할인율이 크면 리워드 하한선을 넘겨 버린다**는 점은 알고 있을 것:

| | 정가 기록(현재) | 실결제액 기록 |
|---|---|---|
| 110,000 원 상품을 50% 할인가 55,000 원에 구매 | 공급가 100,000 원 → **10% 구간 진입** | 공급가 50,000 원 → **10 만원 하한 미달, 0 회** |

즉 런칭 쿠폰에서는 "할인받아 산 사람이 정가 구매자와 같은 리워드 구간"에 들어간다. 5~10% 대에서는
구간 경계에 걸리는 경우가 드물어 거의 무해하다.

**고치기로 하면 거의 공짜다** — ①때문에 `prepare` 가 기대 금액을 서버에 기록하도록 어차피
바꿔야 하고, `fulfill` 이 정가 대신 그 값을 쓰게 하는 것은 한 줄이다. ① 작업할 때 같이 볼 것.
(VAT 는 알아서 따라온다 — `supplyWon(총액)` 이라 총액이 줄면 공급가액도 줄어든다.)

  (`coupon_conflict`) — 받을 자격이 없던 할인이기 때문이다. 보유 제한(duplicate)과 같은 처리다.

    이미지에 얹히거나 입으로 불러 주는 값이라, 옮겨 적다 틀리면 문의가 된다. 직접 입력할
    때는 여전히 전체 글자를 쓸 수 있다.

    이미 쓰인 코드면 그 자리에서 빨갛게 알리고 발급 버튼을 잠근다. 최종 판정은 여전히 발급
    트랜잭션이 한다(두 사람이 동시에 같은 코드를 넣어도 만들어지는 건 하나다).
  100% 는 막는다 — 청구액이 0 이면 결제창이 뜨지 않는다(무료 지급은 리워드 경로가 따로 있다).
- **겹침 검사와 발급을 한 트랜잭션**에 묶었다. 나눠 두면 창 두 개에서 동시에 발급했을 때 둘 다
  통과해 겹친 쿠폰이 생기고, "쓸 수 있는 쿠폰은 최대 한 장"이라는 전제가 깨진다. 경계가
  맞닿는 것(앞 종료 == 뒤 시작)도 그 순간 둘 다 유효하므로 겹침으로 본다.
- 현황은 **잔여 수량**을 같이 내려준다 — 소진 뒤에도 "선착순"을 노출하면 기만적 표시가 된다.
- **삭제 대신 비활성화**다. 이미 등록한 사람의 보유분이 남아 있고, 그 사본은 등록 시점 조건을
  복사해 두므로 계속 쓸 수 있다. 새 등록만 막힌다.
- **사용자 지급은 "이미 발급된 코드를 그 사람 쿠폰함에 넣는" 방식**이다(이용권 지급이 상품표에서
  고르는 것과 같은 모양). 그 사람만을 위한 쿠폰을 즉석에서 만들지 않는다 — 진행 중인 캠페인과
  기간이 겹쳐서 위 전제가 깨진다. 선착순 상한은 **넘겨서 지급**하되(운영자 판단이 마감에 막히면
  안 된다) 카운터는 올려 실제 발급 수와 어긋나지 않게 한다.

> 쿠폰을 뿌리기 최소 7 일 전에 공지를 올려야 한다는 뜻이다(어드민 공지 화면 사용).
> 개인정보처리방침은 손댈 필요 없다 — 수집 항목이 늘지 않는다.

**쿠폰 사용 끄기 (2026-09-25 사용자 결정)**

쿠폰은 1 회용인데 자동 적용이라, **3,000 원 상품에 30% 쿠폰이 소진되면 900 원 할인에 그치고
11 만원 상품에 쓸 기회(33,000 원)가 사라진다.** 고지만으로는 "몰랐다"가 문의로 온다 — 사용자가
스스로 막을 수 있게 했다.

- `prepare` 가 `useCoupon: false` 를 받으면 쿠폰을 고르지 않는다. 클라이언트가 보내는 것은
  **쓸지 말지**뿐이고, 어떤 쿠폰을 쓸지도 얼마를 깎을지도 여전히 서버가 정한다.
- **`/charge` 목업에 "이번엔 쿠폰 사용 안 함" 체크박스 자리가 필요하다.**

**쿠폰함 안내 문구 (확정, 2026-09-25)** — 화면 만들 때 그대로 넣는다.

```

• 쿠폰에 따라 등록 인원이 제한될 수 있으며, 한도에 도달하면 등록할 수 없습니다.

• 쿠폰을 사용한 경우, 보너스 리워드와 친구 초대 리워드는 상품의 원래 가격이 아닌
  할인 가격을 기준으로 합산됩니다.

```

  그건 보유해도 적용되지 않는다.

  있어 무기한 남는다.
- **선착순 안내를 추가.** 마감된 코드를 넣으면 거부 문구가 뜨는데 사전 설명이 없었다.

## 진입 시 "틀린 값 → 맞는 값" 전수 조사 (2026-09-25)

사용자 지시: *"진입 전에 계산 미리 해야 하는 곳 있는지 전체 조사해봐."* 가격이 정가로 떴다가
할인가로 바뀌는 걸 고친 직후였는데, **같은 모양의 버그가 더 있을 것**이라는 판단이었고 맞았다.

### 찾는 대상을 뭐라고 정의했나

"로딩이 느리다"가 아니다. **초기값이 그럴듯한 거짓말인 곳**이다. `null` 로 시작해서 "불러오는
중..."을 띄우는 화면은 멀쩡하다 — 사용자가 "아직 모른다"를 본다. 문제는 `0`, `false`, `[]`,
`""` 로 시작하는 값들이다. 이건 "없다"라는 **사실 주장**이라, 조회가 끝나기 전 수백 ms 동안
화면이 **남의 상태를 내 상태인 양** 보여준다.

### 뿌리 — `authChecked` 와 `loaded` 사이의 창

`RoomsContext` 는 `onAuthStateChanged` 콜백에서 `setAuthChecked(true)` 를 **`getIdToken()`
앞에서** 부른다. 계정에 딸린 값은 그 뒤 `/api/user/me` 로 온다. 그런데
`(app)/layout.tsx` 는 `authChecked` 만 보고 자식을 그렸다 — 그래서 컨텍스트가 텅 빈 채로
서브페이지가 한 번 렌더된다.

앱 안에서 이동할 때는 이미 채워져 있어 안 보인다. **새로고침 · URL 직접 진입 · 결제 실패 후
재진입**에서만 보인다. 그래서 09-25 에 `/api/user/me` 가 `activeCoupon` 을 같이 내려주게 고친
것으로는 **절반만 막혔다** — 앱 내 이동만 닫히고 나머지 경로는 그대로였다.

### 고친 것

| 어디 | 무엇이 거짓이었나 | 조치 |
|---|---|---|
| `(app)/layout.tsx` | 서브페이지 전체 — `activeCoupon=null`·`countPasses=[]`·`hasBirthInfo=false` | `!isChatRoute && !loaded` 면 렌더 보류 |
| `/charge` | 열두 장이 정가 → 할인가. 가격 줄이 한 줄 늘어 이름·설명이 ~12px 밀림 | 위 게이트로 해소 |
| `/charge`·`/received-passes` | 생년월일시를 넣어 둔 사람에게도 자미두수 조합 누르면 `NoBirthTimePopup` | 위 게이트로 해소 |
| `tarot/TarotScreen.tsx` | 컴포저 아래 안내 3줄(생년월일시·궁합 상대·"보유 이용권 없음")이 떴다 사라짐 | 세 자리에 `roomsLoaded &&` |
| `/settings` | 토글 4개가 기본값으로 떴다 저장값으로 뒤집힘 | `initialSnapshot === null` 이면 "불러오는 중..." |
| `/me/profile` | 입력해 둔 사람에게도 빈 폼 | `loaded` 플래그 추가 |
| `/invite` | "가입한 친구: **0**명" | `invitedFriends` 를 `number \| null` 로 |

대화 화면(`isChatRoute`)은 비로그인도 머무는 곳이라 레이아웃에서 통째로 막을 수 없다. 그래서
거기만 자리별로 가드했다 — `noUsableTicket` 이 이미 같은 이유로 `roomsLoaded` 를 보고 있었다.

`/settings`·`/me/profile` 은 단순한 깜빡임이 아니었다. **그 창에서 토글을 누르면 곧 도착하는
응답이 조용히 덮어쓴다** — 분명히 바꿨는데 안 바뀐 게 된다.

### 멀쩡해서 안 건드린 것

`/my-passes`, `/purchase-history`, `/usage-history`, `/notifications`, `/coupons` — 전부 목록
state 를 `null` 로 시작해 "불러오는 중..."을 띄운다. 이 저장소에 이미 있던 올바른 관례고,
위의 수정도 그 관례를 따라 맞췄다.

### 확인 (Playwright, 로컬 dev)

`/api/user/me` 를 3 초 지연시켜 창을 인위적으로 벌린 뒤 대조했다.

- **고치기 전**(`layout.tsx` 만 stash): 1.5 초 시점에 `/charge` 가 정가 열두 장을 **이미 다
  그려 놓고** 있었다. 추측이 아니라 재현이다.
- **고친 뒤**: 같은 시점에 빈 화면, 응답 도착 후 정상 렌더. `/settings`·`/me/profile` 은
  "불러오는 중..." 이 뜬다.

### 대가 — 알고 넘어간 것

`/me/profile`·`/settings` 는 `useRooms()` 를 안 쓰고 **자기가 따로 `/api/user/me` 를 부른다**.
이제 레이아웃 게이트(컨텍스트의 me 조회) 뒤에 자기 조회가 붙어 **새로고침 시 왕복이 두 번**
직렬로 일어난다. dev 기준 `/charge` 728ms vs `/me/profile` 1,615ms. 운영에서는 API 한 왕복
차이로 줄고, 앱 안에서 이동할 때는 컨텍스트가 이미 차 있어 한 번뿐이다. 거슬리면 컨텍스트가
me 원본을 그대로 들고 있게 해 두 페이지가 재사용하면 된다 — 지금은 안 했다.

### 게이트가 만든 새 버그 2개 — 같은 날 잡음 (2026-09-26 새벽)

게이트를 넣자마자 **막으려던 것보다 나쁜 것**이 두 개 생겼다. 둘 다 재현해서 확인했다.

**① `.json()` 이 던지면 모든 서브페이지가 영영 백지**

`RoomsContext` 의 `applyMe(await meRes.json())` 이 맨몸이었다. `.json()` 은 **200 이어도**
던진다(본문이 JSON 이 아닐 때 — 프록시가 가로챈 HTML 등). 바로 아래 방 목록 파싱은 예전부터
같은 이유로 try 에 감싸여 있었는데 여기만 빠져 있었다. 예전엔 콜백이 reject 돼도 화면은 떴다
(`setLoaded(true)` 에 못 닿을 뿐, 레이아웃은 `authChecked` 만 봤으니까). 게이트를 넣으면서
같은 사고가 **전 서브페이지 백지**로 승격됐다. → try/catch.
*재현: me 가 200+text/html 을 주도록 가로채니 `/charge` 가 7 초 뒤에도 백지.*

**② `loaded` 는 "값이 왔다"가 아니라 "요청이 끝났다" — 그래서 돈이 샜다**

me 가 401·5xx 면 `applyMe` 를 건너뛰고 그대로 `setLoaded(true)` 로 흐른다. 게이트가 열리고,
컨텍스트는 **전부 초기값**이다. 오표시로 끝나지 않는다:

`/charge` 는 `activeCoupon` 이 null 이면 **쿠폰 끄기 토글을 아예 안 그린다**(`selected && coupon`).
그런데 `useCoupon` 은 기본값 `true` 로 남아 그대로 전송되고, 서버(`payment/prepare`)는
`useCoupon !== false` 라 보유 쿠폰을 골라 적용·소진한다. **화면은 정가라고 말한 채로 1 회용
쿠폰이 3,000 원짜리에 타 버린다** — 토글을 만든 이유(09-25 결정) 자체가 무력화된다.

`loadFailed` 로 겸할 수 없었다. 저 값은 아래에서 `setLoadFailed(failed)` 로 **방 목록 기준으로
덮어쓰인다** — me 실패를 적어둬도 방 목록이 성공하면 지워진다.

→ **`meFailed` 를 따로 들었다.** 레이아웃은 서브페이지에서 `meFailed` 면 빈 화면 대신
"정보를 불러오지 못했어요 / 잘못된 금액이 보일 수 있어 화면을 열지 않았어요"를 보여준다.
10 초 주기 `refreshMe` 가 성공하면 `meFailed` 가 풀려 화면이 알아서 열린다.
*재현: me 를 401 로 가로채니 안내 화면 → 라우트 풀자 13 초 안에 정상 복귀.*

> **교훈**: "로딩이 끝났다"와 "값이 왔다"를 한 불리언으로 겸하지 말 것. 게이트를 세울 때는
> **게이트가 열리는 모든 경로**를 따라가 봐야 한다 — 실패해도 열리면 게이트가 없느니만 못하다.

**③ 가드를 넣었는데 실패하면 안 열린다 — 화면 7개**

②를 고치고 보니 같은 실수를 화면마다 반복해 두었다. **가드가 성공 경로에서만 열린다.**
`if (res.ok)` 에 else 가 없고, `getIdToken`/`fetch`/`json` 이 던지는 경로도 안 잡는다
(파이어베이스는 `onAuthStateChanged` 콜백의 reject 를 잡아 주지 않는다).

직전에 "확정 건 전부 처리했다"고 적었는데 **사실이 아니었다.** 세어 보니 5 건이 남아 있었다.

| `/signup` | (app) 그룹 **밖**이라 레이아웃 게이트가 안 닿는다. 카카오 닉네임·기존 생년월일이 오기 전 **빈 폼** | 로딩/실패 가드 |

**알림 배지 — 진입 문제가 아니라 마지막 쓰기 승자(last-write-wins)다.** 알림 화면이 mark-read
를 보내고 배지를 끄는데, **그보다 먼저 출발한** `refreshMe` 의 응답이 나중에 도착하면 아직
`true` 라서 배지를 되살린다. 그래서 "언제 껐는가"(`badgeClearedAtRef`)와 "이 응답을 언제
요청했는가"(`requestedAt`)를 비교해 **옛 응답의 `true` 만** 무시한다 — `false` 는 늦게 와도
맞는 말이라 그대로 반영한다. 배지를 끄는 전용 경로 `clearNotificationBadge()` 를 컨텍스트에
두었다(`setHasUnreadNotifications(false)` 를 직접 쓰면 같은 구멍이 다시 생긴다).
*재현: me 응답 하나를 6 초 늦추고 `true` 로 바꿔 보낸 뒤 그 사이에 알림을 읽음 → 낡은 응답이
도착해도 점이 안 켜짐(전에는 켜졌다).*

**사이드바 접힘은 안 고쳤다.** `localStorage` 를 `useState` 이니셜라이저에서 읽는데 서버
프리렌더에서는 항상 `false` 라, 접어 둔 데스크탑 사용자는 한 프레임 펼쳐진 사이드바를 본다.
제대로 고치려면 테마(`THEME_INIT_SCRIPT`)처럼 **페인트 전 블로킹 스크립트**로 `<html>` 에
표시를 남기고 폭·라벨 숨김을 전부 CSS 로 옮겨야 한다 — 지금은 React state 가 클래스 여러 벌을
갈아끼우는 구조라 그 전환이 작지 않다. **데스크탑에서 사이드바를 접어 둔 사람만, 한 프레임**
이라 비용 대비 뒤로 미룬다. 할 때는 테마와 같은 방식으로 묶는 것이 맞다.

### ⑥ 메인에 이전 대화가 남는 버그 (2026-09-26, 사용자 리포트)

*"대화방을 열어둔 상태에서 좌상단 새 대화 버튼을 눌렀더니 메인화면에 대화내용이 뜬다."*

**내 첫 진단은 틀렸다.** 히스토리 이펙트가 `if (!user || !activeRoomId) return;` 으로 빠져나가며
messages 를 안 비우는 게 원인이라 보고 "메인으로 나오면 비우기" 이펙트를 넣었는데 **증상이
그대로였다.** 고쳐도 안 낫는다는 건 원인이 아니라는 뜻이라, 다시 봤다.

**진짜 원인은 비동기 조회의 경합이다.** 경로가 `/` 로 바뀌면 이 화면은 컨텍스트의
`activeRoomId` 가 아직 **옛 방인 채로** 한 번 렌더된다(컨텍스트는 `selectRoom` 이펙트가 돈
뒤에야 null 이 된다). 그 렌더에서 **옛 방의 히스토리 조회가 출발한다.** 그 뒤 화면이 메인으로
정리돼도, 늦게 도착한 응답이 `setMessages` 로 옛 대화를 도로 붙여 넣는다. 내가 넣었던 "비우기"
이펙트는 응답보다 **먼저** 돌아서 아무 소용이 없었다.

→ 이펙트에 **취소 플래그**(cleanup 에서 `cancelled = true`)를 달아 늦게 온 응답을 버린다.
그러고 나니 "비우기" 이펙트는 필요 없어져서 **지웠다** — 없어도 되는지 직접 빼고 다시 재현해
확인했다.

같은 가드가 **방 A → 방 B 를 빠르게 눌렀을 때 B 화면에 A 의 대화가 뜨는** 문제도 같이 막는다.

*확인: 새로 연 메인 본문 204자 / 방 893자 → 고치기 전 "새 대화" 후 **1034자**(환영 문구 + 옛
대화) → 고친 뒤 **204자**. 뒤로가기 경로도 동일. 방 A 히스토리를 4초 지연시키고 A→B 를 빠르게
눌러도 B 의 길이가 안 변함(14387 유지).*

> **교훈 4**: 고쳤는데 증상이 그대로면 **원인을 잘못 짚은 것**이다. 고친 코드를 더 손대기 전에
> 진단으로 돌아갈 것. 그리고 마운트 후 조회에는 **응답이 아직 유효한지** 확인하는 가드가
> 기본값이어야 한다 — 이 세션에서 같은 모양(낡은 응답이 최신 상태를 덮어씀)을 알림 배지에서도
> 봤다.

## "사업 얘기"를 악용으로 오탐 (2026-09-26, 사용자 리포트)

*"지금 만드는 서비스에 추가로 들어갈 과금모델을 개빡세게 만들고 있는데, 이거까지 추가하면
출시 후 수익에 큰 도움이 될까?"* → **"타로 상담 범위를 벗어난 것으로 보입니다"** + 정지 경고.

**이건 타로의 본령이다.** "내가 내린 결정이 잘 될까"는 예로부터 점을 보는 가장 대표적인
이유이고, 이 서비스가 파는 것 자체다. 모델이 소재(사업·수익)만 보고 컨설팅 요청으로 읽었다.

### 왜 단순한 오표시가 아닌가

`NO_CHARGE_MARKER` 가 붙으면 `flaggedForAbuse: true` 로 저장되고, 그 필드는 어드민의
**정지 후보 목록**이 그대로 읽는다(`admin/src/app/api/admin/moderation/route.ts`). 즉 오탐이
정상 결제 사용자를 검토 대상으로 올린다. 사용자에게는 "반복하면 이용이 정지될 수 있다"가
뜬다 — 돈 내고 물어본 사람에게.

### 고친 것

프롬프트 case 2("완전히 무관한 요청")에 가르는 기준을 명시했다. **소재가 아니라 "무엇을
시키는가"다.**

| 무관한 요청 (마커) | "과금 모델을 설계해줘", "손익분기점을 계산해줘" — **AI에게 실무를 대신 시키는 것** |

수치를 지어내지 말고 흐름으로 답하라는 기존 규칙("정확히 얼마를 벌지")과 같은 처리다.

### 재사용할 만한 측정 결과

- **그라데이션 대비는 양 끝이 아니라 경로 위 21개 지점의 최솟값**으로 판정한다.
  OKLab 보간은 중간이 양 끝보다 불리해질 수 있다.
- **호리(hori.chat) 핵심 색상은 312°, 타연 핑크는 3°로 50° 떨어져 있다.**
  보라로 가는 그라데이션은 그 거리를 21°까지 좁힌다. 파랑→핑크는 끝점이 멀어 보여도
  **경로 중간이 3°까지 붙는다** — 끝점만 재면 안 된다.
- **면끼리 갈리는 정도는 명암비로 재면 안 된다.** 명암비는 밝은 쪽에서 눌린다 —
  라이트 1.10 / 다크 1.15로 같아 보이던 게 실제 OKLab 밝기차로는 0.031 대 0.088이었다.
  **OKLab L 차이로 재고 0.06을 기준선**으로 쓴다(면과 페이지는 0.02).
- **WCAG 대비는 초록 편이다.** 상대휘도가 초록에 0.7152, 빨강 0.2126, 파랑 0.0722을 준다.
  같은 OKLab 명도에서 `#00cc82`(Y .448)가 `#ff7aa3`(Y .378)보다 1.18배 밝다.
  **핑크는 같은 대비 역할을 맡으려면 초록보다 밝은 쪽에 놓여야 한다.**
- **치지직 브랜드 사다리는 전 단계가 그 명도의 최대 채도 99%다.** 색조를 고르는 게 아니라
  sRGB 경계선을 따라간다. `#ff007f`도 C 0.260 / max 0.262 = 99%로 같은 규칙의 색이다.
  대비로 풀면 `#ff007f`는 치지직 체계의 **채움 면 자리**(다크 weaker / 라이트 weak)다.
- **다크 본문은 일부러 낮춘다.** 거의 검정 위 `#f4eef0`(16.70)은 획이 번진다(헐레이션).
  AA의 네 배쯤 가면 눈이 부시다.
- `doc/design/build-point-ramp.mjs`가 공용 도구다 — `contrast` / `toOklch` / `oklch` /
  `rgbToHex` / `RAMP`를 내보낸다. 다른 생성기들이 전부 여기서 가져다 쓴다.

### 비용 방어 — Claude 리딩 요청 제한 (정책 확정 후 구현)
- 목적: 시간제 이용권이 있더라도 무제한 고비용 API 호출, 매우 긴 입력, 대화방 대량 생성으로 발생하는 모델·DB 비용을 방어한다.
- 서버에서 인증된 UID 기준으로만 집계하며, 화면의 비활성화만으로는 판단하지 않는다. 제한 초과 시 Claude 호출과 이용권 차감을 모두 하지 않고, 재시도 가능 시각을 포함한 429 응답을 반환한다.
- 적용 대상/후보값: 질문 본문 최대 1,000자, 리딩 시작은 1분당 10회·24시간당 100회, 대화방은 계정당 100개. 실제 숫자는 Claude 모델별 단가·정상 사용 로그를 보고 확정한다.

- 개인정보가 포함될 수 있는 원문 질문은 비용 분석 원장에 복제하지 않는다. UID 직접 식별값 대신 집계키 또는 가명화 키를 사용하고, 운영 통계에는 최소 표본 기준을 둔다.

### 환불 요청 및 검증 결과
- 사용자 결제내역에 `환불 요청` 기능을 추가하고, 요청은 관리자 환불요청 페이지에 쌓는다. 목록에는 닉네임, UID, 이용권명, 이용권 가격, 구매 일시(초 단위), 결제수단 세부 정보(카드사/간편결제 등), 요청 사유·시각·상태를 표시한다.
- 현재 구현 검토 결과:
  - 구매내역 화면은 이미 결제 후 7일 이내이면서 이용권 상태가 `unused`일 때만 `환불하기` 링크를 보여 준다. 횟수제 1회 이상 사용 또는 시간제 활성화 뒤에는 링크가 숨겨진다.
  - 다만 그 링크는 현재 고객센터(`/support`)로 이동할 뿐 사용자 환불 요청 API·UI·관리자 요청 목록은 아직 없다. 관리자가 결제를 직접 취소하는 API만 있다.
  - 관리자 직접 취소 API에서는 결제일 7일 초과, 잔액/이용권 사용 여부가 아직 **경고**일 뿐 취소를 막지 않는다. 향후 환불 요청 처리 API에는 같은 기준을 서버에서 하드 차단하고, 예외 환불은 별도 승인·사유·감사 로그 흐름으로 분리해야 한다.
  - 시간제 이용권은 `unused`가 아니면 관리자 API에서 경고만 한다. 횟수제 이용권은 관리자 환불 처리에서 회수/차단 분기가 없어 보완이 필요하다.
  - 결제 레코드에 카드사·간편결제 등 결제수단 상세를 저장하지 않아, 환불요청 목록 요구사항을 충족하지 못한다. 포트원 결제 확정 시점에 안전한 표시용 결제수단 정보를 저장해야 한다.
  - PG 취소 성공 뒤 DB 갱신 실패 시 상태 불일치가 생길 수 있으므로, 취소 요청 감사 로그와 재시도 가능한 상태 전이를 둔다.

- **Haiku 4.5 vs Sonnet 5 실측 비교 후 Haiku 유지 결정**: "사주/자미두수/궁합 중 하나라도 켜지면 Sonnet을 쓰면 어떨까"라는 아이디어를 실제 API로 검증. 최악 조합(켈틱크로스+사주+자미두수+궁합) 기준 Haiku 22~30초·22~23원 vs Sonnet 기본 72~155초·87~189원(재시도 포함) — Sonnet 5가 요청 안 해도 기본적으로 adaptive thinking을 켜서(484~3004 thinking 토큰) 응답이 크게 느려지고 비싸짐. `thinking: {type:"disabled"}` + `effort: "low"`로 재테스트하니 36~48초·47~89원까지 개선됐지만, 그래도 Haiku 대비 1.5~3배 느림 — 사용자가 "그래도 너무 오래 걸린다"고 판단해 채택 안 하기로 결정. 대신 지금처럼 Haiku를 유지하면서 사주/자미두수 통합 품질 문제는 발견될 때마다 프롬프트 규칙으로 보강하는 기존 방식을 계속 쓰기로 함

  - reauth 필요 → `gcloud auth application-default login`
  - quota project 미설정 → `gcloud auth application-default set-quota-project <project>`

- **⚠️ ADC 만료는 "로컬 전체가 고장난 것"처럼 보인다 (2026-09-23, 2026-09-25 두 번 겪음)**
  — 자격증명이 서비스 계정 키가 아니라 `authorized_user` 타입이라 주기적으로 죽는다
  (`invalid_grant / reauth related error (invalid_rapt)`). 죽으면 `verifyIdToken` ·
  `createCustomToken` · Firestore 읽기가 **동시에** 실패하는데, `getUidFromRequest` 가 모든
  예외를 null 로 뭉개서(`src/lib/auth/verifyRequest.ts`) 화면엔 그냥 401 로만 보인다.
  증상: 방 목록 401 → 메인이 "대화를 불러오지 못했어요", 카카오 콜백 500(토큰 교환·프로필
  조회까지는 정상이고 그 다음 Firestore 접근에서 죽는다), 이용권 조회 실패가 한꺼번에 온다.
  **토큰이 무효한 게 아니라 서버가 액세스 토큰을 아예 못 만드는 상태다 — 로그아웃시키면 안 된다.**

  복구는 PowerShell 에서. **ADC 경로가 기본 위치가 아니라 `.gcloud-tayeon` 으로 잡혀 있다**
  (`.env.local` 의 `GOOGLE_APPLICATION_CREDENTIALS`) — 그냥 로그인하면 `%APPDATA%\gcloud\` 에
  저장돼서 로그인은 성공했는데 앱은 계속 죽은 옛 파일을 읽는 상황이 된다:

  ```powershell
  $env:CLOUDSDK_CONFIG="C:\Users\redte\.gcloud-tayeon"
  gcloud auth application-default login
  gcloud auth application-default set-quota-project tayeon-d5149
  ```

  bash 식 `VAR=x command` 인라인 접두사는 PowerShell 에서 파서 에러다. quota project 는 새
  로그인 파일에 안 들어오므로 다시 붙여야 한다. 그리고 **dev 서버를 반드시 재시작한다** —
  `src/lib/firebase/admin.ts` 가 모듈 로드 시점에 자격증명을 한 번만 잡아서, 파일만 갈아끼우면
  떠 있는 서버는 계속 옛 것을 쓴다. 진단은 `firebase-admin` 으로 Firestore 읽기와
  `createCustomToken` 을 직접 찔러 보면 즉시 갈린다(둘 다 같은 에러면 ADC 문제다).
- 테스트 계정은 `firebase-admin`으로 커스텀 토큰 발급 → Identity Toolkit REST API로 ID 토큰 교환하는 방식으로 curl 테스트함 (실제 브라우저 로그인 없이도 API 테스트 가능)
- **에뮬레이터로 "로그인한 화면"을 여는 법 (2026-09-24 추가)** — 카카오 로그인은 실제 콘솔·도메인이

## 환불 흐름 전면 정비 (2026-09-24)

사용자가 "환불 신청 후에도 이용권이 그대로 있다"고 지적한 데서 시작해, 법령 대조 → 약관 수정 →
자동 승인 → 운영 알림까지 이어졌다. 커밋 7개.

### 1. 발견한 것 — 돈이 새는 구조

**환불을 신청해도 이용권이 그대로 쓸 수 있었다.** 신청 → 사용 → 환불이면 공짜다.

신청 시점에 이용권을 **`refund_pending`** 으로 잠근다(요청 접수와 같은 트랜잭션). 플래그가 아니라
**새 상태**로 만든 이유는 실패 방향이 다르기 때문이다 — "쓸 수 있나" 검사가 전부 `unused`/`active`
만 보므로, 빠뜨린 경로가 있어도 **못 쓰게 되는 쪽으로** 틀린다. 플래그였다면 빠뜨린 곳이 그대로
뚫린다.

전체 코드에서 상태를 읽는 곳을 훑어 두 종류로 갈랐다:

| 성격 | 예 | `refund_pending` |
|---|---|---|
| **쓸 수 있는가** | `/me` 이용권 목록, 시간제 활성화, 리딩 차감 | **제외**(자동) |
| **보유 중인가** | 중복 구매 차단, 어드민 보유 표시 | **포함**(`HELD_PASS_STATUSES`) |

파생 문제 둘도 같이 고쳤다 — 어드민 승인이 `unused` 만 받아 **사용자 요청을 승인할 수 없었고**,
거절 시 잠금을 안 풀어 **돈은 받았는데 못 쓰는 이용권**이 됐다.

### 2. 법령 대조 — 약관 4곳이 무효 소지

korean-law MCP 로 전자상거래법·약관규제법을 직접 읽었다. 유사 서비스 3곳(호리, 사주나루,
헬로우봇) 약관도 대조했다.

**청약철회는 승인/거절 대상이 아니다.** 제17조②는 "통신판매업자의 **의사에 반하여**" 철회할 수
없는 경우를 열거하는데, 뒤집으면 그 밖에는 사업자 의사와 무관하다. 제17조④는 발송한 날 효력
발생, 제18조②2호는 **청약철회한 날**부터 3영업일, 제17조⑤는 다툼 시 **사업자가 증명**.

| 조항 | 문제 | 근거 |
|---|---|---|
| 제9조3항 | "환불이 **승인된 건은**" 3영업일 | 약관규제법 제9조1호·5호 |
| 제9조2항 | 요건 미충족 시 "거절할 수 있습니다" | 제9조1호 |
| 제6조4항 | "**부정확성**"을 환불 사유에서 배제 | 제17조③ 배제 → 제9조1호 |
| 제13조·제6조3항 | 고의·중과실 단서 없는 면책 | 약관규제법 **제7조1호** |

헬로우봇에만 있던 두 조항(제17조⑥ 사전표시 의무, 제18조② 지연배상금)을 가져와 신설했다.
호리·헬로우봇은 **청약철회 제한 근거를 제18조②로 잘못 인용**하고 있다(맞는 조문은 제17조②).
기산점도 "회수한 날"로 써서 디지털콘텐츠용 2호가 아닌 재화용 1호를 적용했다 — **업계 관행에
오류가 복제되고 있다.**

**의도적으로 안 고친 것**: 제9조1항의 "1회라도 사용하면 환불 제한". 횟수제는 가분적이라
제17조②5호 단서상 잔여분은 철회 대상일 가능성이 높지만, 3사 모두 같고 사용자가 관행을
따르기로 결정했다(2026-09-24).

**미이행 확인**: 제13조② "계약내용 서면 교부"(11개 항목)를 하지 않고 있다. PG 승인 메일은
제8조③(결제 사실 통지)을 이행할 뿐 다른 의무다 — 메일 본문에도 "해당 쇼핑몰과는 별도로
발송됩니다"라고 적혀 있다. 서면 미교부면 7일 기산점이 제17조①**2호**(주소를 안 날)로 밀려
앱의 7일 제한 근거가 약해진다. 사용자가 후순위로 미뤘다.

### 3. 자동 승인 (드라이런)

승인이 사람 주의력에 달려 있으면 3영업일 기한을 못 지킨다. 접수 후 **2영업일**(비영업일 제외)이
지나면 자동 승인한다 — 법정 기한보다 항상 최소 1영업일 앞선다.

**기본은 드라이런이다.** `REFUND_AUTO_APPROVE=on` 을 켜기 전에는 판정·알림만 한다.

`refundRisk.ts`(순수 함수, 테스트 9개)가 보류를 결정한다: 이용권 미잠금 / 포트원 상태가 PAID
아님 / 금액 불일치 / 결제 후 10분 내 요청 / **최근 3일 내 2건**. 보류는 거절이 아니라 사람에게
넘기는 것이고, 어떤 조건이 걸렸는지 알림에 싣는다.

환불 실행은 `admin/src/lib/refundExecute.ts` 한 곳에 모았다(수동 버튼 = 자동 승인, 라우트 96줄
감소). 스케줄러(`functions`)는 호출만 한다 — 포트원 SDK 를 거기 또 넣으면 **돈 움직이는 코드가
세 벌**이 되고 토스페이먼츠 교체 때 전부 고쳐야 한다.

### 4. 운영 알림 (디스코드)

`src/lib/notify/owner.ts` — Discord 주, 메일은 `warn`/`urgent` 만. Resend 무료 100통/일을
고객센터 문의가 같이 쓰기 때문에 하루 60통으로 제한해 몫을 남긴다. Discord 실패 시엔 등급과
무관하게 메일 폴백(채널이 죽은 걸 모르는 게 제일 위험하다). 고객문의는 별도 채널.

어드민은 사본을 두지 않고 본체의 `/api/internal/notify` 를 공유 시크릿으로 호출한다.

> 🐛 **알림이 한 건도 안 나가고 있었다.** 키가 `refund-requested/{paymentId}` 인데 Firestore 는
> 문서 id 의 `/` 를 경로 구분자로 읽고 예외를 던진다. `notifyOwner` 의 try/catch 가 그걸 삼켜서
> **에러도 안 보이고 알림도 없는** 상태였다. 내가 앞서 "HTTP 204 발송 성공"으로 확인했던 건
> 웹훅에 직접 쏜 것이라 정작 깨진 부분을 안 거쳤다 — **테스트가 실제 경로를 덮지 않으면 통과가
> 의미 없다.** 키 변환 + 테스트 4개로 고정했고, 첫 수정이 또 틀린 것(`__proto__` → `___proto__`
> 도 예약 패턴)도 그 테스트가 잡았다.

`void` 대신 `next/server` 의 **`after()`** 를 쓴다. 응답 후 작업 실행을 보장하는 공식 API다.

### 5. 어드민 사각지대

구매분인데 요청이 `pending` 이 아닌 건(메일 접수분, 거절 후 재처리)은 **어드민에서 손댈 방법이
없었다.** 요청 목록은 pending 만, 회수는 `admin-grant` 만 대상이다(구매분 회수는 돈을 안 주고
뺏는 것이라 맞는 제한). 사용자 상세의 이용권에 **환불** 버튼을 달았다.

포트원이 "이미 취소된 결제"라고 답하면 **실패가 아니라 정합화**로 처리한다. 운영자가 콘솔에서
직접 취소했거나 웹훅이 유실되면 이 상태가 되는데, 오류로 끝내면 이용권이 `refund_pending` 에
갇힌다. `refundReconciled` 플래그로 "우리가 취소함"과 "뒤늦게 맞춤"을 구분해 둔다.

### 6. 알아둘 것

⚠️ **TEST 채널 결제도 카드 승인이 일어난다** — 실제로 카드사 사용 알림이 온다(사용자 확인).
포트원 기록은 `channelType=TEST`/`isTest=true` 로 남지만, 테스트 결제는 반드시 취소해서
정리할 것. 실제 청구(매입)까지 가는지는 카드 명세서로 확인해야 한다.

⚠️ `admin/.env.local` 의 **`PORTONE_API_SECRET` 이 비어 있었다**. 운영(`admin/apphosting.yaml`)
에도 빠져 있으면 어드민 환불이 아예 안 된다 — 배포 전 확인 필요.

### 7. 아직 검증 못 한 것

- **자동 승인의 실제 동작** — 스케줄러·어드민·본체 세 앱이 물려 있어 배포 후에야 확인된다.
  판정 로직(`refundRisk`)은 테스트 9개로 덮여 있다.
- **어드민 수동 환불은 알림을 안 보낸다** — 자동 승인 경로만 보낸다. 필요하면 추가.
- 거절 → 재요청 → 알림 목록 표시까지의 전체 흐름을 한 번에 이어서 보지는 못했다.

## 결제 전반 어뷰징·정상처리 감사 (2026-09-24)

환불 정비에서 "우회가 되거나 정상처리가 안 되거나 어뷰징이 가능한 곳이 또 있나"를 물어
결제 경로 전체를 훑었다. 진단마다 **반증 전담 에이전트**를 붙여 검증했고(10건 중 반증 0,
5건은 내가 과장했던 것으로 판정), 6개 렌즈로 추가 sweep을 돌려 19건을 더 찾았다.

### 내가 과장했던 것 — 기록해 둘 만한 교훈

- **"자동승인 실패 알림이 매시간 온다"는 정반대였다.** `assessRefundRisk`가 먼저 hold를
  걸고, `notifyOwner`는 키를 **영구** 중복제거한다. 알림이 딱 한 번 오고 그 뒤 침묵한다.
  폭탄이 아니라 조용히 갇히는 쪽이고, 그게 더 위험했다.
- **`freePasses`는 어느 화면에서도 렌더링되지 않는다.** "받은 이용권 내역에 17회로 뜬다"는
  틀렸다. 화면에 안 나오는 필드로 심각도를 매기지 말 것.
- **자동취소된 결제는 어드민에선 보였다**(유저 상세가 status 필터 없이 읽어 "중복 취소"로
  표시). 사용자도 정상 경로에선 409로 안내받는다. 사각지대는 웹훅 단독 처리 경우뿐.
- NaN은 JSON에서 null이 된다 — "NaN이 보인다"가 아니라 "숫자 없이 단위만 보인다"가 증상.

### 고친 것

| 문제 | 원인 | 조치 |
|---|---|---|
| 리워드 받고 환불 (말일 3일간) | 정산(5일)이 환불창(7일) 안에 있었음 | 정산일 → **매월 10일**. 8일은 6시간 모자람(구간 경계가 `Date.UTC` 자정=09:00 KST라 구간 마지막 결제가 "다음달 1일 08:59") |
| **환불 요청 교착** | 신청은 7일까지 받는데 집행이 `Date.now()`로 7일 재검사. 자동승인이 2영업일 뒤라 금요일(4일차) 신청이 화요일(8일차)에 409 | 기산점을 **요청 시각**으로. `admin/src/lib/refundWindow.ts` 로 분리 + 테스트 5개 |
| 지급 불가 결제가 돈만 먹음 | 거부 8종이 취소·기록·알림 전부 없음 | `autoCancel` 플래그 + 자동취소 + 알림. **uid 불일치는 false** — 아니면 남의 결제를 취소시키는 통로 |
| 자동취소 건이 결제 내역에 안 뜸 | `orderBy("fulfilledAt")` — 그 필드가 없는 문서는 Firestore가 통째로 제외 | `paidAt` 정렬 + 배지 + 취소 실패 시 urgent 알림 |
| 환불 요청 영구 pending | 탈퇴로 payment 문서 소멸 / 콘솔 직접취소 후 409 | 탈퇴 차단 + 이미 환불된 건은 요청만 완료 처리 |
| **만료 이용권이 재구매를 영구 차단** | `status:"expired"`를 써 주는 코드가 없어서 만료분이 계속 `unused` | `isHeldPass()` — 상태 + 유효기간. 약관도 만료 후 재구매를 약속함 |
| **자기 추천** | 내 초대링크로 탈퇴→재가입하면 `referredBy`에 내 uid. 매달 본인 결제의 5%를 본인에게 | 카카오 콜백에서 `referredBy === uid` 차단 |
| **가입 리워드 반복 수령** | 멱등 키가 추천인-친구 **쌍**이라 추천인만 바꾸면 계속 받음 | 받는 사람 기준 최상위 마커 `referralSignupGrants/{uid}` (TTL 없음) |
| 리딩 500 (토큰 쓰고 버림) | 후보를 `remaining>0`로 고르고 차감은 스프레드별 환산 → 모델 호출 다 끝낸 뒤 던짐 | 후보 선택에 스프레드 감당 여부 반영 + 모델 호출 전 402, 경합 시 409 |
| 리워드 횟수 표기≠지급 | 단가 200→300 미반영 6곳 | `basisForOneCardCount()` 역산 (4조합×60횟수 테스트). 생일쿠폰은 조합배율 이중적용으로 **광고의 절반**이었음(200 시절에도 틀렸던 계산) |
| 알림 영구 유실 | `claim()`이 발송 **전에** 키를 커밋 | 전 채널 실패 시 키 해제 |
| 자동승인 배치 기아 | `limit(20)` 무정렬 → 매시 같은 20건 | `orderBy("requestedAt","asc")` |
| 어드민 목록에서 오래된 대기 건 소실 | 전체에서 최근 100건 후 브라우저 필터 | 상태별 조회 |
| 부분 취소 무통보 | `ignored`로 흘려보냄 | `kind:"partial"` 구분 + urgent 알림 |
| 어드민 시간제 지급 이중 발급 | `["unused","active"]` 복제본이 `refund_pending` 누락 | `isCurrentlyHeld()` 재사용(유효기간까지) |
| 환불 거절 ↔ 승인 경합 | 거절이 트랜잭션에서 요청 문서를 재확인 안 함 | 재확인 + 409 |
| 대화방 삭제 불가 | 배치 1개 = 상한 500. 리딩 많은 방은 영구 삭제 불가 | 450개씩 쪼갬 |
| pg-review 로그인 무제한 대입 | 제한·상수시간비교 없음 | IP별 15분 10회 + `timingSafeEqual` |
| `orderName`을 브라우저에서 받아 기록 | 어드민·알림에 사실처럼 표시 | 서버가 정한 `product.orderName` |
| 죽은 코인 차감식 | `!chosenPass` ⟹ `spreadCovered`라 항이 전부 0 | 식 + 상수 3개 제거 |

인덱스 3개 추가(`firestore.indexes.json`) — **배포 전 `firebase deploy --only firestore:indexes` 필요.**

### 안 고친 것 — 판단이 필요하다

- **생일쿠폰 파밍** — `birthdayCouponGrants` 원장 키가 사용자 생일이 아니라 **실행일**이고
  `birthdayMMDD`는 사용자가 매일 바꿀 수 있다(카카오 생일 동의항목 심사 중이라 지금은
  `kakaoBirthday`를 가진 유저가 0명). 카카오 심사 통과를 기다리기로 함.
- **생일쿠폰 수령 UI** — `options`에 타로 전용이 없는데 선택 카드는 4조합을 다 그린다.

### 리워드 횟수 환산 개편 (2026-09-24)

무상 지급 이용권이 제 가치보다 많이 나가고 있었다. `countAllowance` 가 `basis ÷ 단가` 와
`× 조합배율` 에서 각각 반올림하는데, 올림이 겹치면 작은 리워드일수록 후해진다 — **최대 3.98배**
(5만원 결제 보너스 750원이 3,000원짜리 스타터 한 장 값). 금액이 커져도 2배 언저리가 남았다.

**구매분과 규칙을 갈랐다.** 구매는 공표 가격표(`PUBLISHED_COUNT_TABLE`)가 그대로 진실이고,
무상 지급은 `rewardAllowanceForCombo` / `rewardAllowancesForCombo` 가 진실이다.

1. **버림.** 어떤 금액에서도 basis 가치를 넘지 않는다(1.00배 상한).
2. **같은 스프레드에서 조합이 비쌀수록, 같은 조합에서 카드가 많을수록 최소 1회는 적게.**
   버림만으로는 동률이 남는다(basis 3,600 에서 켈틱+사주와 켈틱+자미가 나란히 3회). 비싼 조합이
   싼 조합과 같은 횟수를 주면 조합을 나눈 의미가 없다 — 사용자 확정 규칙.
3. **공표표를 타지 않는다.** 리워드 basis 는 300의 배수라 상품 basis 중 3,000(스타터)과
   135,000(얼티밋) 두 곳에 정확히 겹치는데, 그 두 지점만 공표표로 빠지는 바람에 **리워드를 더
   받았는데 쓸 수 있는 횟수가 줄어드는 역전**이 있었다(basis 3,000 → 3,300 에서 쓰리카드 3칸 감소).
   상품 가격표를 개정할 때마다 리워드 지급량이 딸려 움직이는 결합도 이걸로 끊었다.

이 규칙은 사용자가 손으로 잡아준 두 표(원카드 3회분 / 12회분)를 **N=3 은 16/16, N=12 는 14/16**
재현한다. 남은 2칸(양자택일 열)은 규칙값이 1 높은데, 표를 따로 관리하지 않는 쪽을 택했다.

**적용 범위** — 리워드 2종(보너스·친구 결제), 친구 초대 가입 보상, 생일 쿠폰, 어드민 **커스텀**
지급. 어드민이 상점 상품을 그대로 지급하는 건(productId 있음)은 구매와 같아야 하므로 공표표를
계속 쓴다. 가입 무료체험(combo:"any")은 16칸 고정 4회라 무관하다.

**최소 기준 금액을 둘 다 10만원으로** (사용자 결정)

- 보너스 요율표에서 5만원/1.5% 구간 제거 → 최저가 10만원/3%
- 친구 결제 리워드에 `REFERRAL_MONTHLY_MIN_WON = 100_000` 신설. 추천인의 친구들 **월 합산**
  기준이며 미달분은 이월하지 않는다(`functions/src/index.ts` 의 정산 루프에서 skip)
- 초대 화면 문구에 기준선을 넣고, 예시를 10만원 → 20만원으로 올렸다 — 예시 금액이 기준선과
  같으면 "10만원이면 받는다"와 "10만원부터 받는다"가 한 문단에서 부딪힌다

**`rewardPassesForWon` 도 버림으로** (2026-09-24, 사용자 결정). 예전엔 반올림이라
`basis = round(원금/300) × 300` 이 커미션보다 최대 150원 많았다(친구 10만원 → 커미션 5,000원인데
basis 5,100). 이제 **basis 가 커미션을 넘는 구간이 0** 이다 — 금액 → 회수 → 칸 배분 세 단계가
모두 버림으로 일관된다. 대가로 33% 구간에서 표기 회수가 1 줄어든다(친구 10만원 17 → 16회,
보너스 20만원 27 → 26회). 초대 화면 예시(20만원 → 33회)는 그대로다.

커미션은 원 단위 정수로 먼저 확정한다 — 0.07 같은 요율이 부동소수점에서 `56000.00000000001` 로
떨어지는데, 반대로 어긋난 값이 버림과 만나면 한 회가 조용히 사라진다. 테스트로 고정해 뒀다.

`apphosting.yaml` 두 개에 빠져 있던 변수를 전부 채웠다. 두 파일 다 YAML 파싱·중복 검사 통과.

| 대상 | 추가 |
|---|---|
| `apphosting.yaml` (본체) | `INTERNAL_API_SECRET`, `DISCORD_WEBHOOK_URL`, `DISCORD_SUPPORT_WEBHOOK_URL` (시크릿) · `ADMIN_BASE_URL` |

`INTERNAL_API_SECRET` 은 **어디에도 없던 값**이다 — 어드민→본체 알림(`/api/internal/notify`)이

functions 의 `hourlyRefundAutoApprove`(어드민 호출).

**배포 전에 반드시 먼저 실행할 것** (시크릿 3개가 Secret Manager 에 아직 없다. 없는 시크릿을
참조하면 **롤아웃이 실패한다**). 값은 `.env.local` 에 있다:

```
firebase apphosting:secrets:set INTERNAL_API_SECRET --project tayeon-d5149 --force
firebase apphosting:secrets:set DISCORD_WEBHOOK_URL --project tayeon-d5149 --force
firebase apphosting:secrets:set DISCORD_SUPPORT_WEBHOOK_URL --project tayeon-d5149 --force
```

`--force` 가 생성·권한부여·YAML 추가를 한 번에 한다. YAML 은 이미 넣어 뒀으니 중복 항목이 생기면
지울 것. 등록 후 `gcloud secrets list` 로 7개 → 10개가 됐는지 확인.

**백엔드 3개** — `apphosting:backends:list` 의 `ABIU` 열은 **자동 출시가 아니라 기본 이미지 자동
업데이트**다. 자동 출시 설정은 CLI 에 안 나오고 `traffic` 리소스의 `rolloutPolicy` 에 있다:

```
GET https://firebaseapphosting.googleapis.com/v1beta/projects/tayeon-d5149/locations/asia-east1/backends/{id}/traffic
```

| 백엔드 | rootDirectory | 추적 브랜치 | 자동 출시 |
|---|---|---|---|
| `tayeon` | `/` | `live` | ON |
| `tayeon-qa` | `/` | `qa` | ON |
| `tayeon-admin` | `/admin` | `live` | ON |

`rolloutPolicy` 에 `disabled` 가 없으면 자동 출시 ON 이다. **셋 다 ON 이고 경로 필터는 없다** —
`requiredPaths`/`ignoredPaths` 필드가 스키마에는 있지만 세 백엔드 모두 미설정이다(콘솔 "출시
트리거" 입력란에 보이는 `src/app/*` 같은 값은 저장된 설정이 아니라 **플레이스홀더 예시**다).

셋 다 서비스 계정은 `firebase-app-hosting-compute@tayeon-d5149.iam.gserviceaccount.com` —
시크릿 접근 권한은 이 계정에 준다.

**⚠️ `tayeon-admin` 도 `live` 를 추적한다.** 심사 중 `live` 동결이 어드민 배포까지 막고 있다는
뜻이고, 반대로 **`live` 를 올리는 순간 본체와 어드민이 같이 자동 배포된다.** 그 전에 시크릿 3개가
등록돼 있지 않으면 두 롤아웃이 모두 실패한다.

**functions 도 같은 값이 필요하다** — `hourlyRefundAutoApprove` 가 `ADMIN_BASE_URL` 과
`INTERNAL_API_SECRET` 을 읽는다. `functions/` 에는 `.env` 가 없어서 배포 시 따로 넣어야 한다.

### 마이페이지·리워드 모달·내 보유 이용권 (2026-09-24 목업 반영)

목업 10장(`asset/Screen/New/` 의 MyPage / RewardInfoModal_Expect / RewardInfoModal_Percent /
MyPass_Held / MyPass_Send × 다크·라이트)을 받아 구현했다.

**마이페이지** — 계정 카드에서 "횟수제 이용권 + 구입" 행을 뺐다(이용권 섹션의 "내 보유 이용권"이
그 역할을 받는다). 보너스 리워드 값은 회수가 아니라 **요율**을 보여준다 — 회수는 조합마다 달라서
한 줄에 담을 수 없다. 기준 미달이면 "0%" 가 아니라 **"미지급"** 이다.

**보너스 리워드 모달** — 예상 리워드 / 리워드 비율 두 탭. 예상 탭은 조합 4종을 좌우로 넘겨
보면서 각 조합이 실제로 줄 횟수를 보여준다(오늘 만든 무상 지급 규칙을 예상 basis 에 물린다).

**⚠️ 리워드는 공급가액(VAT 제외) 기준으로 바뀌었다** (사용자 결정). 안내 문구는 처음부터
"VAT 제외" 였는데 계산만 총액이어서, 사용자가 낸 세금까지 리워드로 돌려주고 있었다.
요율 구간 판정과 지급 회수 **둘 다** 공급가액을 쓴다.

`1.1` 로 나누지 않는다 — `110000 / 1.1` 이 이진 부동소수점에서 `99999.99999999999` 로 떨어져서
**딱 10만원어치를 결제한 사람이 최저 구간에 못 들었다**(110만원 결제도 10% 가 아니라 7%).
`× 10 / 11` 로 11의 배수를 정확히 떨어뜨린다. 경계값은 테스트로 고정.

즉 **"10만원 이상" 구간에 들려면 총액 110,000원을 결제해야 한다.**

**내 보유 이용권** — `/my-passes`(보유) + `/received-passes`(받은 내역) **두 경로 + 공용 하단
탭바**(`src/components/MyPassTabs.tsx`)로 만들었다. 한 화면에 상태로 묶지 않은 이유: 받은 내역
쪽이 수령 흐름(조합 선택 → 받기)과 모달 두 개를 들고 있어서 옮기면 그 흐름을 다시 검증해야
한다. 경로를 나누면 각자 자기 상태를 쓰고, 알림에서 "리워드 도착" 을 수령 탭으로 보내는 것도
링크 하나로 끝난다.

`/api/user/held-passes` 신설. `/api/user/me` 도 보유분을 주지만 그건 앱 전체가 계속 부르는
경로이고, 무엇보다 **환불 신청 중인 이용권을 의도적으로 뺀다**(쓸 수 없으므로). 보유 목록은
반대로 반드시 보여야 한다 — 신청해 둔 이용권이 앱 어디에도 없으면 사라진 것처럼 보인다.

**환불 취소 신설** (사용자 지시). 접수는 쉬운데 물릴 길이 없어서, 마음이 바뀌어도 2영업일 뒤
자동 승인으로 결제가 취소됐다. `POST /api/user/refund-requests/{paymentId}/cancel` —
접수의 정확한 반대로 "요청 종료 + 이용권 잠금 해제" 를 한 트랜잭션에 묶는다. 요청 문서는
`cancelled` 로만 바꾸고 지우지 않는다(분쟁처리 기록 3년). 취소한 건은 **다시 신청할 수 있다**.
버튼은 결제 내역의 "환불하기" 자리와 보유 목록 양쪽에 있다.

**목업과 다른 점 두 가지**

- 목업 하단 "매월 5일에 지급됩니다" → 코드는 `REWARD_PAYOUT_DAY_OF_MONTH` 에서 뽑아 **10일**.

  더 낮고 0회 칸도 생긴다(사용자 확인: 0회로 표시).

**아직 안 한 것** — "내 보유 이용권" 목업이 두 탭을 한 화면으로 그리고 있는데 구현은 경로 2개다.
