## 1. 확정된 결정

| 이미지 모델 | **gpt-image-2.5-flare**, `1024x1536` / `low` | 세로가 정사각보다 싸고, low와 medium이 육안 구분 불가 |
| 성인 전용 상품 | **없다**(2026-09-26 철회) | 아래 「성인 표시를 뗀 이유」 참고 |

**용어:** 기획 문서의 "카드"는 이 문서에서 **섹션(section)** 으로 부른다. 같은 코드베이스에 타로가 있고
거기 `TarotCardInfo` / `CardImage` 가 실재해서, `card` 를 쓰면 반드시 충돌한다.

### 성인 표시를 뗀 이유 (2026-09-26 결정, 사용자)

속궁합·성향 두 상품에 `adultOnly: true` 가 붙어 있었다. **근거가 없었다.**

- **법적 의무가 아니다.** 청소년보호법 제2조제3호의 「청소년유해매체물」은 청소년보호위원회나
  심의기관이 유해하다고 **결정하고 고시한 것**만이다. 우리 상품은 고시된 바 없으므로 제16조의
  「나이 및 본인 여부 확인」 의무도 걸리지 않는다. 내용도 성행위 묘사가 아니라 성향과 대화
  가이드라 심의 기준이 겨냥하는 종류가 아니다.
- **실제 이유는 다른 것이었다.** 이 표가 적어 둔 대로 "카드사 심사 중 결제 상품 목록 변경
  리스크"였고, 심사가 live 에서 돌고 작업은 main 에서 하므로 그 전제가 성립하지 않는다.

대신 **성인 전용으로 읽히던 문구를 고쳤다.** 그대로 두고 전 연령에 파는 건 앞뒤가 안 맞는다 —
상품 자신이 성인용이라고 말하고 있으면 분쟁 때 그 문구가 근거가 된다. `성인 간`·`성적`·`욕구`·
`19금` 을 걷어냈고, 슬러그도 `bdsm-compatibility` → `skinship-compatibility` 로 바꿨다(제목에서
19금을 뺐는데 주소창에 BDSM 이 뜨면 앞뒤가 안 맞는다. 저장된 리포트가 없을 때라 공짜였다).

**안전 제약은 남겼다.** 「별도 테스트는 제공하지 않는다 … 실제 선호·경계는 반드시 당사자 간
대화로 확인해야 한다」는 `constraints` 로 **모델에 전달되는 값**이다(주석이 아니다). 성인 표시를
뗀 것과 성향을 단정하지 않게 하는 것은 다른 얘기다.

### 총평은 마지막이다 (2026-09-26 결정, 사용자)

기획 3.2 의 권장 흐름은 `한 줄 총평 → …` 으로 총평이 맨 앞이었다. **뒤집는다.**

- 맨 앞의 총평은 아직 아무것도 읽지 않은 사람에게 결론을 먼저 던지는 것이다. 읽을 이유를 없앤다.
- 뒤에 두면 총평이 **본문을 근거로 쓸 수 있다.** 10섹션이 실제로 무슨 말을 했는지 받아서 쓰므로,
  골격 단계에서 예측으로 쓰는 총평보다 정확하다.

그래서 이름이 겹치는 두 가지를 갈라 둔다. 섞으면 반드시 혼동된다.

| | 무엇 | 화면 |
|---|---|---|
| `outline.thesis` | 1단 골격이 만드는 **내부 기준**. 섹션 생성과 근거 배정이 이걸 보고 쓴다 | **노출 안 함** |
| 0페이지 | **목차 + 미리보기** — 섹션 제목 10개와 한 줄 요지 | 첫 화면 |
| 마지막 페이지 | **총평** — 전 섹션을 받아 쓰는 결론 | 끝 |

`thesis` 는 화면에 안 쓰더라도 **계속 만든다.** 이게 섹션 간 중복을 막고 근거 배정을 만드는
장치라서다(§5 의 부처궁 10/10 → 2/10 이 그 효과다). 화면 비노출과 생성 불필요는 다른 얘기다.

**부수 효과 — 0~29초 공백이 줄어든다.** 총평 문단을 먼저 스트리밍할 필요가 없으니 JSON 필드
순서를 `sections → thesis → …` 로 두면 목차가 더 빨리 도착한다(§6 미해결 ①). *미실측.*

### 원가

| 항목 | 값 |
|---|---|
| 1단 골격 (Sonnet 5) | 약 **33원** |
| 2단 섹션 10장 (Sonnet 5, 순차, 캐시 적용) | 약 **163원** (장당 14~20원) |

> **이 표는 확정치가 아니라 계획 수치다(2026-09-26 사용자 결정).** 같은 입력을 넣어도 모델이
> 쓰는 길이가 매번 달라서, **한 번 더 재도 확정되지 않는다.** 섹션 10장이 14~20원으로 흩어져
> 있는 것이 그 폭 그대로다.
>
> 그래서 실측이 주는 것은 확정치가 아니라 **자릿수가 맞는지에 대한 확신**이다. 판매가(8,900~
> 19,900원) 대비 원가가 2% 수준이라는 판단에는 그 확신이면 충분하고, 20원 안팎의 차이는
> ± 범위로 둔다. 이미지 8원만은 실제 청구액과 대조해서 맞춘 값이다.

> **⚠️ 합계에 3단 총평이 빠져 있었다(2026-09-26 두 번째 정정).** 실측 11회 호출은 골격 1회 +
> 섹션 10회이고 **총평은 그 안에 없다**(`.tmp/saju/report4.json` 의 usage 객체가 정확히 11개다).
> 그런데 총평은 옵션이 아니라 **모든 리포트의 마지막 페이지**라 편당 원가에 반드시 들어간다.
> 그걸 빼고 197 + 8 = 205원으로 적어 뒀던 것을 224원으로 고쳤다. 판매가를 정하는 숫자라
> 한 항목이 빠지는 것이 그대로 마진 오차가 된다.
>
> 총평 20원은 **예상치로 남는다.** 입력이 골격 + 섹션 요지 10개라 뒤쪽 섹션(20원)과 비슷할
> 것으로 보는 것인데, 위 「계획 수치」 주의대로 **재 봐도 확정되지는 않는다.** 빠져 있던 것이
> 문제였지 예상치인 것이 문제가 아니다 — 합계에서 한 항목이 통째로 없으면 마진 계산이 어긋난다.

**이 숫자가 어디서 왔나.** 토큰 수는 실측이고 원 금액은 계산이다 — 다음 번에 모델이나 단가가
바뀌면 이 절차만 다시 돌리면 된다.

- **실측**(`.tmp/saju/report*.json`, API 가 돌려준 `usage` 그대로): 순차 11회 호출 합계가
  입력 17,949 · 캐시적중 17,072 · 출력 9,670 토큰. 캐시 기록은 0(앞선 실행이 이미 써 둠).

- **계산**: 위 토큰에 Sonnet 5 단가와 환율 **1,450원/$** 를 적용 → $0.1360 = 196원

### ⚠️ 캐시는 **5분**만 산다 (2026-09-26 발견, 미반영)

공식 가격표를 대조하다 나왔다. *"prompt caching pricing reflects **5-minute TTL**"* —
프롬프트 캐시의 기본 수명이 5분이고, 더 긴 것은 별도 옵션이다.

**위 실측은 이 함정을 지나쳐 갔다.** 스크립트가 11회 호출을 연달아 돌렸으므로 5분 안에 다 끝났고,
그래서 캐시가 전부 적중했다(`cr 17,072`). 그런데 **실제 사용은 그렇지 않다** — 우리는 페이지를
온디맨드로 만든다(§6). 사용자가 1페이지를 읽는 동안 2페이지를 만들고, 그 사이 간격은 **읽는
속도**가 정한다. 10페이지짜리를 20분에 걸쳐 읽으면 뒤쪽 섹션과 총평은 **캐시가 죽은 뒤에** 만들어진다.

| | 편당 |
|---|---|
| 전부 적중 (실측이 잰 것) | **224원** |
| 전부 실패 (읽는 속도가 느릴 때) | **약 281원** |

차이는 공통 블록 17,072 토큰이 캐시 읽기($0.20/1M)가 아니라 캐시 쓰기($2.50/1M)로 계산되는
데서 온다. **25% 다.** 판매가의 2~3% 사이라 당장 위험한 수준은 아니지만, §2 의 숫자가 **가장
좋은 경우**라는 것은 적어 둬야 한다.

**확인·대응은 실호출 검증에서 한다**(§11):
- 실제로 몇 번째 섹션부터 캐시가 죽는지는 읽는 속도에 달렸으므로, 스크립트에 **간격을 주고**
  돌려 봐야 안다. 지금 스크립트는 연달아 돌린다
- **긴 수명 캐시 옵션**이 있다. 쓰기 비용이 비싼 대신 한 번 쓰고 오래 산다 — 우리처럼
  "한 번 쓰고 20분에 걸쳐 여러 번 읽는" 모양에는 그쪽이 맞을 수 있다. 실측 없이 고르지 말 것

## 3. 구조

화면 이름은 **운세**(`fortune`)이고 도메인 이름은 **사주**(`saju`)다. 갈라 둔 것은 의도다 —
사용자가 보는 말은 "운세"인데, 라이브러리·컬렉션·이 문서가 전부 "사주"로 쓰여 있다. 라우트를
`saju` 로 맞추면 화면에 없는 말이 주소창에 뜨고, 라이브러리를 `fortune` 으로 맞추면 자미두수까지
포함하는 이름이 아니게 된다.

```
src/app/(app)/fortune/
  page.tsx                     상품 목록
  [slug]/page.tsx              상품 소개 + 구매
  readings/[id]/page.tsx       결과 뷰어 (생성중·완료·실패 전부 여기)
src/app/api/saju/
  readings/route.ts                   POST 주문 생성 → 계산 + 골격
  readings/[id]/route.ts              GET 상태/저장분
  readings/[id]/pages/[n]/route.ts    GET 저장분 / POST 없으면 생성해서 저장 후 반환
  readings/[id]/closing/route.ts      POST 총평 (마지막 페이지)
  readings/[id]/image/route.ts        POST 이미지 (재생성 포함)
```

### 상품은 코드가 아니라 데이터

기획 문서의 19개 상품이 **전부 같은 모양**이다. 이건 우연이 아니라 이 설계의 가장 큰 자산이다.
**두 번째 상품부터는 파일 하나 추가가 전부**여야 한다.

```ts
export type SajuCategory = "인생" | "연애" | "궁합" | "결혼·가족" | "직업·재물" | "건강·인간관계";

export type SajuProduct = {
  slug: string;
  categories: SajuCategory[];             // 여러 개에 걸린다 — 아래 절 참고
  tag: string;                            // 카테고리가 아니라 상품을 가리키는 짧은 말
  pricesWon: { saju: number; ziwei: number; integrated: number };
  title: string; subtitle: string; description: string;
  userInputPrompt: string;
  purpose: string;                        // "목적·핵심 질문"
  sections: { id: string; title: string }[];
  sajuFocus: string;                      // 기획 문서의 "사주 중점" 문단 그대로
  ziweiFocus: string;
  crossPoints: string;
  image: null | { subject: string; elements: string[] };
  needsPartner: boolean;
  adultOnly?: boolean;
  constraints?: string;                   // 기획의 "분석 방식" — 모델에게 주는 안전 제약
};
```

`constraints` 는 19개 중 **BDSM 상품 하나만** 가진다. 주석으로 적어 두면 모델에 전달되지 않는데
이건 안전 제약이라, 시스템 블록이 **문체 규칙보다 앞**에 꽂는다(`generate/outline.ts`).

`sajuFocus` 같은 걸 **파싱하지 않고 문자열 그대로 프롬프트에 꽂는다.** 문서에 쓰인 한국어가
이미 LLM이 읽을 지시문이라, 중간에 구조화하면 정보만 잃는다.

### 상품은 카테고리 **여러 개**에 걸린다 (2026-09-26, 사용자 상품표)

`category` 단수가 아니라 `categories: SajuCategory[]` 다. "관련 있는 카테고리에서 다 뜨게" 하려는
의도라 한 상품이 여러 곳에 걸린다 — 예: `결혼` 은 인생·결혼·가족·연애 세 곳, `성격` 은 궁합·연애·
건강·인간관계 세 곳.

상품 카드 표기는 **`카테고리들 · 태그`** 이고(`연애 · 궁합 · 썸`), **맨 뒤 한 칸만 태그**다. 배열
순서가 곧 표기 순서다. 태그는 카테고리가 아니라 상품을 가리키는 짧은 말(`솔로`, `재회`, `배우자`)
이라 `tag` 로 따로 둔다.

> 목업 `Fortune_Home_Dark` 의 속궁합 카드는 `연애 · 궁합 · 속궁합` 인데 상품표는 `궁합, 연애`
> 순이다. **상품표를 단일 출처로 본다** — 목업 카드의 순서는 예시로 읽는다.

### 판매가 (2026-09-26 확정, 변동 가능)

| | 사주 | 자미두수 | 통합 |

## 5. 생성 파이프라인

```
결제확정 → 계산 → [1단] 골격 1회 → [2단] 섹션 순차 N회 → [3단] 총평 1회
                        └→ 이미지 (image_brief 나오는 즉시 병행)
```

### 1단 — 골격

출력 순서: `sections[]`(요지 + **근거 배정**) → `thesis`(내부 기준) → `usedMetaphors` → `image_brief`

목차가 먼저 도착하도록 `sections` 를 맨 앞에 둔다(§1 "총평은 마지막이다").

**근거 배정이 핵심이다.** 이걸 안 하면 연애 상품의 모든 섹션이 부처궁만 쳐다본다.
1단에서 섹션마다 쓸 궁·십신을 미리 나눠준다.

| | 배정 없음 | **배정 있음** |
|---|---|---|
| 부처궁 인용 | 10/10 섹션 | **2/10** |
| 거문 | 9 | 1 |
| 등장한 궁 종류 | 3개 | **11개** |
| 원가 | 185원 | 194원 |

**품질 개선이 사실상 공짜였다.**

### 2단 — 섹션 순차

각 섹션은 골격 + **앞 섹션들이 실제로 쓴 것**(제목·첫 문장·사용한 종결어미)을 받는다.
전문을 넘기지 않아서 입력 증가가 미미하다 — 병렬(194원)보다 3원 비싼 197원에 그쳤다.

| | 병렬 | **순차** |
|---|---|---|
| 해요체 유지 | 46% | **70%** |
| 최다 종결어미 비율 | 14% | 16% |
| 서로 다른 궁 | 11종 | 11종 |
| 전체 생성 | 46초 | 147초 |
| **첫 페이지까지** | 46초 | **42초** |

### 3단 — 총평 (미실측)

마지막 섹션까지 끝난 뒤 1회. 입력은 골격 + **각 섹션이 실제로 쓴 결론(`summary`) 10개**다.
본문 전문은 넘기지 않는다 — 2단이 앞 섹션 전문을 안 넘겨도 됐던 것과 같은 이유다.

사용자가 10~11페이지를 읽는 동안 만들면 되므로 **지연은 보이지 않는다.** 원가는 섹션 1개
수준(약 20원)으로 예상하지만 재보지 않았다.

### 프롬프트에 반드시 박을 것 — 안 하면 망가진다

1. **`thinking: { type: "disabled" }`** — 기본값이 켜져 있다. 첫 실행에서 출력 3,000토큰 중
   **2,955가 thinking** 이라 본문이 한 글자도 안 나왔다. 모르고 붙이면 원가가 3~4배.
2. **문체를 해요체로 못 박을 것.** "앞에서 쓴 종결어미를 쓰지 마라"만 넣었더니 모델이 금지 목록을
   피하려고 **해요체를 통째로 버리고 `~한다` 문어체로 도망갔다**(해요체 0%). 어미를 기계적으로
   금지하면 문체가 무너진다. "해요체는 유지하되 그 안에서 굴려라"로 써야 한다.
3. **이미지 브리프의 대상을 명시할 것.** 안 쓰면 **내담자 본인**을 그린다. 상품은 "들어올 인연의
   예상 모습"인데 첫 실행에서 `"혼자 창가에 앉아 미소짓는 여성"` 이 나왔다.
4. **소제목에 섹션 이름을 그대로 쓰지 말 것.** 빼먹으면 `"관계 발전의 흐름: 천천히 쌓여…"` 가 나온다.
5. **일치 상태값은 지정된 5개만.** 이건 지시대로 100% 지켜졌다(위반 0건). 퍼센트도 안 만들었다.

### 프롬프트 캐시

시스템 블록(상품 정의 + 명반 근거)에 `cache_control: ephemeral`. 섹션 호출이 전부 공유한다.

> **Haiku 는 캐시가 안 걸린다.** 시스템 블록이 1,642토큰인데 Haiku 4.5 의 최소 캐시 길이는
> 2,048이다(Sonnet은 1,024). 측정된 Haiku 125원은 캐시 없는 값이다.

## 6. 전달 — 페이지와 시간

### 해결된 부분

한 섹션이 **660자**, 읽는 데 1분 안팎. 생성은 **10~14초**.
**읽는 속도가 생성 속도를 절대 못 따라잡는다.** 1페이지를 다 읽을 때쯤 2~6페이지가 쌓여 있다.

이미지도 **골격만 나오면(29초) 바로 시작**할 수 있다. 섹션 생성과 병행하면 사용자가
마지막 페이지에 도달할 때 이미 준비돼 있다. **이미지를 맨 뒤에 붙이지 말 것.**

### 미해결 ① — 0~29초 구간

0페이지(목차) 완성이 28.9초다. **그 앞의 28초가 빈다.** 지금 화면은 그 구간에 "불러오는 중..."만
띄운다 — 여기가 §6 에서 유일하게 남은 구멍이다.

> **실측의 "총평 첫 글자 2.1초"는 그때의 골격이 총평을 먼저 썼기 때문이다.** §1 에서 총평을
> 마지막 장으로 옮겼으므로 지금 골격의 첫 출력은 `sections` 다. 즉 **2.1초에 오는 것이 목차의
> 첫 줄**이고, 아래 첫 번째 대책은 그만큼 더 유리해졌다. 28.9초라는 완성 시점은 그대로다.

대책 두 가지:

- **스트리밍으로 목차를 한 줄씩 채운다.** 필드 순서가 이미 `sections` 가 맨 앞이라(§1 부수 효과)
  목차가 순서대로 도착한다. 타로 카드 뒤집히듯 차오르는 연출이 된다. 다만 지금 1단은
  `messages.parse` 로 **완성된 JSON 을 한 번에** 받으므로, 이걸 하려면 스트리밍 파싱이 필요하다.
- **골격을 둘로 쪼갠다.** 요지만 먼저(짧아서 ~10초), 근거 배정은 뒤에서 조용히.
  0페이지가 29초 → 10초로 당겨진다. *미실측.*

### 닫힘 ② — 누가 147초를 돌리나 (2026-09-26 구현)

순차 생성은 전체 147초다. 이걸 **사용자 요청 하나에 붙여 두면 안 된다.** 사용자가 앱을 나가면
죽고, 함수 타임아웃에도 걸린다.

**페이지 단위 온디맨드 + 선행 요청(prefetch)으로 지었다.** 각 요청이 10~14초짜리 독립 호출이라
타임아웃에 안전하고, **백그라운드 워커·큐가 없다.** 사용자가 나가면 그냥 멈추고, 다시 오면
저장된 데까지 보고 이어서 부른다.

지으면서 계획과 달라진 것, 그리고 계획에 없던 제약이 생긴 것을 아래에 적는다.

#### 돈이 나가는 일은 POST, 읽기는 GET

**계획은 `GET /pages/3` 이 "없으면 만들어서 준다"였다. 그렇게 지으면 안 된다.**

| 호출 | 하는 일 | 비용 |
|---|---|---|
| `GET .../pages/{n}` | 저장분만 읽는다. 없으면 404 `not_generated` | **공짜** |
| `POST .../pages/{n}` | 없으면 만든다 | **약 17원** |

GET 은 **주소만 알면 눌리는 것**이다. 브라우저 prefetch·크롤러·실수로 열어 둔 탭·새로고침이
전부 모델을 부르게 되고, 그게 전부 과금이다. "부작용이 있으면 GET 이 아니다"라는 규칙이 여기서
돈으로 직결된다. 총평(`POST .../closing`)과 이미지(`POST .../image`)도 같은 이유로 POST 다.

#### prefetch 는 N+1 **한 장**뿐이다

계획은 "N+1, N+2를 미리 부른다. 버퍼 2장이면 충분하다"였는데 **한 장으로 줄였다.**

한 장 읽는 시간(약 1분)이 한 장 만드는 시간(10~14초)보다 훨씬 길다. 그래서 두 장을 앞서 당겨도
**사용자가 기다리는 시간은 더 줄지 않고 과금만 앞당겨진다** — 중간에 그만 읽는 사람에게는 만들
필요가 없었던 장이 된다. 버퍼를 늘려서 얻는 것이 없다는 것이 §2 의 시간 실측에서 나온다.

#### 총평은 **이미지 장에 들어설 때** 건다

총평은 전 섹션의 결론을 받아 쓰므로 마지막 섹션이 끝나야 만들 수 있는데, 그때 시작하면 사용자가
**마지막 장에서 그대로 기다리게 된다.** 그래서 한 장 앞인 이미지 장 진입에서 미리 건다 — 그림을
보는 동안 만들면 지연이 보이지 않는다. **이미지가 없는 상품은 마지막 섹션 진입에서** 건다.

이 판단은 화면이 한다. 라우트는 "언제 부를지"를 모른다.

#### `missing_previous` 자가 회복에는 **상한이 있어야 한다**

N페이지는 N-1까지 있어야 만들 수 있고(§7 의 게이트), 어긋나면 서버가 409 에 빠진 번호를 담아
준다. 화면은 그 번호부터 채우고 다시 시도한다 — 정상 흐름에서는 안 나지만(앞 장을 읽어야 뒤로
온다) 주소를 직접 치거나 앞 장 생성이 실패한 뒤 새로고침하면 난다.

**여기에 반드시 두 개의 제동이 필요하다.** 없으면 POST 가 무한히 나가고 그대로 과금이 샌다.

1. **반복 상한** — 서버가 매번 같은 번호를 돌려주는 경우.
2. **`missing` 이 앞 번호일 때만 따라간다(엄격히 감소).** 게이트는 늘 `n-1` 을 주지만, 자기
   번호가 오면 **진행 중인 자기 요청을 기다려 영구 교착**이고(이미 in-flight 맵에 있다), 두
   번호가 서로를 가리키면 맞물려 멈춘다. 그 실패는 **에러도 없이 화면이 조용히 멎는 것**이라
   로그에도 안 남는다 — 제일 나쁜 종류다.

#### 총평의 미완성 응답은 **번호로** 받는다

`POST .../closing` 을 너무 일찍 부르면 409 `sections_incomplete` 와 함께 **빠진 번호 배열**이
온다. 처음엔 개수(`remaining`)였는데 번호로 바꿨다 — 개수에서 번호를 역산하려면 "1..N 이 연속으로
찬다"를 믿어야 하고, 그 전제가 깨지는 날 화면이 **조용히 엉뚱한 페이지를 만든다.**

#### 오케스트레이션은 React 밖에 있다

페이지 구성·prefetch·총평 시점·중복 요청 방지는 `sajuReaderCore.ts` 에 있고 **React 가 한 줄도
없다.** 훅(`useSajuReader.ts`)은 `useSyncExternalStore` 로 그걸 읽는 껍데기다.

이유는 테스트다. 이 로직이 결정하는 것은 전부 **POST 를 몇 번 보내는가**인데, 저장소에 React
렌더러(`react-test-renderer`·jsdom)가 없어서 훅 안에 있으면 `node --test` 로 부를 수 없다.
의존성을 새로 들이는 대신 로직을 떼어냈다. 부수 효과로 **브라우저 없이 전달 계층을 돌릴 수 있다.**

중복 요청 방지가 왜 테스트로 고정돼야 하는지: 중복 POST 는 그대로 중복 과금인데 **화면에 에러로
뜨지 않는다.** 사용자에게는 "가끔 좀 느림"으로만 보이고 요금을 봐야 드러난다. 실제로 이 자리에서
`useCallback` 이 낡은 클로저를 잡아 같은 장을 두 번 만드는 버그가 한 번 나왔다.

> **과금을 POST 횟수로 세면 안 된다.** 게이트에 걸린 409 는 모델을 부르기 전에 돌아오므로
> **공짜다**. 그래서 회복 경로는 정상 동작에서도 같은 번호에 POST 를 두 번 보낸다(409 한 번,
> 성공 한 번). 세야 하는 것은 **실제로 생성된 횟수**다 — 대리 지표는 처음엔 맞다가 조용히
> 어긋나고, 그때 "테스트는 통과하는데 요금이 올라간다"가 된다.

#### 구매 전 미리보기가 여기를 다시 쓸 수 있다

환불 문구를 전자상거래법 **제17조제2항제6호**(주문에 따라 개별 생산되는 재화)로 옮기면서
**미리보기(시험 사용)를 실제로 만들기로 했다**(2026-09-26). 그게 생기면 구매 전 화면이 장 하나를
읽기 전용으로 보여 주게 될 가능성이 크다.

장별 컴포넌트가 이미 갈라져 있어서(`ReaderToc`·`ReaderSection`·…) 그때 **껍데기만 바꿔 끼우면
된다** — 미리보기는 prefetch 도 총평도 필요 없으니 코어를 통째로 쓰지 않고 컴포넌트만 가져가는
쪽이 맞다. **지금 만들지 않는다. 목업이 먼저다.**

### 닫힘 ③ — 읽던 위치 저장 (2026-09-26 구현)

리포트가 최대 21장이라 한 번에 다 읽지 않는다. 이동할 때마다 `PATCH .../last-read` 로 장 번호를

유무로도 달라져서, 서버가 그걸 다시 계산하면 판정이 두 벌이 된다). 화면이 clamp 한다.

### 실패한 페이지도 문서로 남긴다 (2026-09-26)

§9 는 "섹션 N 이 3회 실패해도 **나머지는 멀쩡하다**"고 정했는데, §6 의 온디맨드 생성은
**N 을 만들려면 N-1 이 있어야 한다**(2단이 앞 섹션이 쓴 것을 받아 중복을 피하므로). 둘을
그대로 두면 3번 섹션이 영구히 죽었을 때 4번부터 끝까지 전부 막힌다 — 18섹션짜리를 19,900원에
팔고 3장을 주는 꼴이다.

그래서 **실패도 페이지 문서로 저장한다.** 게이트가 "존재한다"로 보고 뒤가 풀린다.
`kind` 를 판별자로 두고, 본문 필드를 빈 문자열로 채우지 않는다 — 그러면 "생성 실패"와
"모델이 짧게 씀"을 구분할 수 없고 뷰어가 빈 페이지를 그린다.

실패 자리표에는 제목을 넣지 않는다. 뷰어는 `outline.sections[n-1]` 에서 가져온다.
그리고 다음 섹션에 넘길 "앞에서 쓴 것"을 만들 때 **`kind === "section"` 만 골라야 한다**.

**계산 결과 원본(`chart`)을 반드시 같이 박는다.** 나중에 계산 로직이나 라이브러리가 바뀌어도
**그때 뽑은 판 그대로** 다시 볼 수 있어야 한다. 돈 받고 판 결과가 재접속하면 달라지는 건 사고다.

## 8. 이미지

- `1024x1536` / `low` / 158토큰 / 8초 / **8원**
- 저장 전에 **webp 재인코딩**(1024폭 q82 → 66KB). 방식은 `scripts/build-pass-art.cjs` 와 동일.
- 프롬프트에 **실존 인물 재현 금지 + 글자 삽입 금지**를 항상 붙인다(기획 문서 6.5).
- 화면에 **"명리 해석을 바탕으로 그린 예상 이미지"** 고지를 둔다.

### 다시 뽑기를 기능으로 연다

장당 8원이라 **10번 다시 뽑아도 80원**이다. 9,900원 상품에서.
실패 보상이 아니라 **셀링포인트**로 내세우는 게 낫다. 해석은 그대로고 그림만 다시 그리므로
결과의 일관성도 안 깨진다.

### 바이트는 Firebase Storage 가 아니라 Firestore 에 둔다 (2026-09-26 결정)

기본값은 Storage 가 맞아 보인다 — 파일을 두라고 있는 곳이다. 그런데 이 저장소에는 **Storage
업로드 코드가 한 줄도 없다.** `firebase/admin.ts` 는 `adminAuth`/`adminDb` 만 내보내고
`storageBucket` 은 클라이언트 config 한 줄뿐이다. 쓰려면 버킷 배선 + 보안 규칙 + **URL 정책**을
지금 새로 정해야 한다.

셋 중 URL 정책이 진짜 문제다. 돈 받고 파는 리포트의 이미지를 **공개 URL** 로 두면 주소만 알면
누구나 본다. **서명 URL** 은 만료되므로 화면이 갱신 경로를 따로 가져야 한다. Firestore 에 두고
우리 라우트로 내보내면 **접근 제어가 공짜로 정확하다** — 문서가 `users/{uid}` 아래에 있어서
남의 것은 애초에 읽히지 않는다.

크기는 문제가 아니다. webp 66KB 이고 base64 로 부풀어도 약 88KB, 문서 한도 1MB 의 10분의 1 이다.

| | 값 |
|---|---|
| 저장 위치 | `users/{uid}/sajuReadings/{id}/assets/image` |
| `image.url` | `/api/saju/readings/{id}/image` — **버전을 주소에 넣지 않는다** |
| 다시 뽑기 | 같은 주소, **ETag 만 바뀐다**(`regeneratedCount`) |
| 캐시 | `private, no-cache` — "캐시 금지"가 아니라 "쓰기 전에 물어보라" |

**되돌릴 수 있다.** 바깥에서 보이는 건 `image.url` 하나이고 그것도 이미 우리 라우트 주소다.
Storage 로 옮기려면 `imageStore.ts` 와 라우트만 바꾸면 된다.

대가: 이미지를 볼 때마다 Firestore 문서를 한 번 읽는다(CDN 이 아니다). 한 편에 한 장이고
ETag 로 대부분 304 라 실제 호출은 거의 없다.

## 9. 실패와 환불

| 상황 | 처리 |
|---|---|
| 계산 실패 | 생성 시작 전이므로 자동 전액 환불 |
| 골격 실패 | 자동 재시도 3회 → 실패 시 자동 전액 환불 |
| 섹션 N 실패 | **그 페이지만** 조용히 재시도. 나머지는 멀쩡하다 |
| 섹션 3회 실패 | 그 페이지에 안내 + 운영자 알림. 전액 환불은 부적절(이미 읽었다) |
| 이미지 실패 | 무료 재시도. 환불 없음 (8원이라 사실상 무제한) |

전액 환불의 경계는 **"사용자가 아직 아무것도 읽지 않았는가"** 다.

### 이 표에 없던 두 가지 (2026-09-26, 구현하며 발견)

**① 재시도 3회가 사실상 1회였다.** 실패의 흔한 원인이 429(사용량 제한)와 과부하인데 그건
시간이 지나야 풀린다. 즉시 세 번 치면 세 번 다 같은 이유로 죽고, 그 상태로 실패 자리표가
박히면 **잠깐의 혼잡 때문에 그 페이지가 영구히 안내로 남는다.** 재시도 사이에 1.5초를 둔다.

그래도 10분짜리 장애가 나면 그 사이 생성된 리포트들이 통째로 안내 페이지를 갖는다. 그래서
`producePage({ retryFailed: true })` 로 **자리표를 다시 만들어 보는 문**을 열어 뒀다.

> **사용자에게 주는 버튼이 아니다.** §9 의 "3회 실패면 안내만"은 유효하다 — 같은 조건에서
> 네 번째도 실패한다. 이건 **조건이 바뀐 뒤**를 위한 운영용 문이고, 없으면 복구 수단이
> Firestore 손수정뿐이다. **본문이 이미 있는 페이지는 이 값으로도 못 덮는다** — 사용자가
> 읽던 문장이 바뀌는 건 어떤 이유로도 안 된다.

**② 섹션이 전부 실패하는 경우가 표에 없다.** §9 는 섹션 **하나**가 죽는 경우만 다룬다.
전부 죽으면 총평의 입력이 비는데, 그대로 모델을 부르면 **근거 없이 결론을 지어내고** 그게
저장돼 `complete` 가 된다 — 아무것도 못 읽은 사용자에게 그럴듯한 총평 한 장만 주는 꼴이라
제일 나쁜 결과다. 그래서 총평을 만들지 않고 **운영자에게 urgent 알림**을 보낸다.

돈은 받았고 읽을 게 없으므로 환불 판단이 필요한데, 그 판단을 자동화하지 않았다. 여기까지
오는 건 리포트 한 편이 통째로 실패했다는 뜻이고 그때는 원인부터 봐야 한다.

## 10. 판매 제약 — 결제 전에 막아야 할 것

### 성별 필수

- 사주 **대운은 성별 없으면 계산 자체가 안 나온다**(`manseryeok` 이 gender 없으면 생략).
- 자미두수는 명궁 산출에 관여하는데, 지금 `unspecified` 를 **남성으로 때우고 있다**
  (`src/lib/ziwei/calculate.ts`).
- 타로에선 "선택안함"이 허용이었지만, **유료 사주 상품 구매 플로우에서는 필수 입력으로 막는다.**

### "시간 모름"은 자미두수·통합을 팔지 않는다

지금 `ziwei/calculate.ts` 는 시간을 모르면 **정오로 때운다.** 타로 첨부용일 땐 괜찮았지만,
시진이 틀리면 **명궁이 통째로 다른 궁으로 간다.** 리포트 전체가 다른 사람 얘기가 된다.

- **시간 모름 → 사주 모드만 판매.** 시주만 빼고 해석하면 되므로 성립한다.
- "명궁 정확도가 낮을 수 있습니다"라고 고지하고 파는 건, 환불 요구가 들어오면 지는 싸움이다.

### 섹션 수는 기획 문서와 다르다

솔로 연애는 결과 항목이 **11개**인데 제목은 "권장 10개"다. 마지막 `들어올 인연의 예상 모습` 이
이미지 섹션이다. 따라서 **텍스트 10 + 이미지 1** 로 읽는다. 이미지 섹션은 5단 구조를 갖지 않는다.
