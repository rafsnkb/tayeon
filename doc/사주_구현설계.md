## 1. 확정된 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 코드 위치 | 타연 안 `src/app/(saju)` 라우트 그룹 | 로그인·결제·쿠폰·환불·알림 인프라 재사용. 상품·과금만 분리 |
| 첫 구현 범위 | **솔로 연애 1개 수직 슬라이스** | 계산→생성→결제→화면→환불을 한 상품으로 관통 |
| 생성 방식 | **2단 생성**(골격 → 섹션) + **섹션 순차** | 섹션 간 중복을 막는 유일한 구조 |
| 전달 방식 | **섹션당 1페이지**, 읽고 넘기기 | 생성 시간을 읽는 시간 뒤로 숨김 |
| 텍스트 모델 | **Claude Sonnet** | 원가가 판매가의 3%라 Haiku로 아낄 이유 없음 |
| 이미지 모델 | **gpt-image-2.5-flare**, `1024x1536` / `low` | 세로가 정사각보다 싸고, low와 medium이 육안 구분 불가 |
| 성인 상품(속궁합·BDSM) | 설계에 포함, **출시 시점은 별도 판단** | 카드사 심사 중 결제 상품 목록 변경 리스크 |

**용어:** 기획 문서의 "카드"는 이 문서에서 **섹션(section)** 으로 부른다. 같은 코드베이스에 타로가 있고
거기 `TarotCardInfo` / `CardImage` 가 실재해서, `card` 를 쓰면 반드시 충돌한다.

## 2. 실측 결과

2026-09-26, 샘플 1996-04-12 14:30 여성 / 솔로 연애 통합모드 10섹션.

### 원가

| 항목 | 값 |
|---|---|
| 텍스트 10섹션 (Sonnet, 순차, 캐시 적용) | **약 300원** |
| 이미지 1장 (1024×1536 low, 158토큰) | **8원** |
| **편당 합계** | **약 308원** |

단가 역산: 이미지 출력 **$30/1M**, 텍스트 입력 **$5/1M**.
이미지 15장 9,239 output 토큰 → $0.2885, 실제 청구 $0.29 와 일치. *공식 가격표 대조는 아직 안 함.*

### 시간

```
  2.1s  총평 첫 글자 (스트리밍)
 28.9s  0페이지 완성 — 총평 + 10섹션 목차
 41.9s  1페이지
 54.3s  2페이지
  ...   이후 10~14초 간격
147.3s  10페이지
```

이미지는 별도 8~11초. 3연속 생성에서 거부·실패 0회.

### 이미지 사이즈·품질 매트릭스 (output 토큰 = 과금 단위)

| 사이즈 | low | medium | high |
|---|---|---|---|
| 1024×1024 | 196 | 439 | 1,756 |
| **1024×1536** | **158** | 343 | 1,372 |
| 1536×1024 | 158 | 343 | 1,372 |
| 512×512 | 거부 — 최소 해상도 미달 | | |
| auto | 229 | 472 | 1,372 |

- **세로가 정사각보다 싸다.** 픽셀은 1.5배인데 토큰은 더 적다.
- **1024가 바닥.** 더 줄일 수 없다.
- **`auto` 는 손해.** 명시 안 하면 비싼 쪽이 걸린다.
- 결과 PNG가 1.9MB라 **webp 재인코딩 필수** — 1024폭 q82에서 66KB(28분의 1).

## 3. 구조

```
src/app/(saju)/
  page.tsx                     상품 목록
  products/[slug]/page.tsx     상품 소개 + 구매
  readings/[id]/page.tsx       결과 뷰어 (생성중·완료·실패 전부 여기)
src/app/api/saju/
  readings/route.ts                  POST 주문 생성 → 계산 + 골격
  readings/[id]/route.ts             GET 상태/저장분
  readings/[id]/pages/[n]/route.ts   GET 해당 페이지 (없으면 생성해서 저장 후 반환)
  readings/[id]/image/route.ts       POST 이미지 (재생성 포함)
src/lib/saju/
  calculate.ts                 기존 — 팔자·십신·공망
  fortune.ts                   신규 — 대운·세운·월운
  products/index.ts            상품 레지스트리
  products/single-love.ts      상품 1개 = 파일 1개
  generate/outline.ts          1단
  generate/section.ts          2단
  generate/image.ts
src/lib/ziwei/
  calculate.ts                 기존 — 명궁·신궁·오행국·12궁
  horoscope.ts                 신규 — 대한·유년·사화
```

### 상품은 코드가 아니라 데이터

기획 문서의 19개 상품이 **전부 같은 모양**이다. 이건 우연이 아니라 이 설계의 가장 큰 자산이다.
**두 번째 상품부터는 파일 하나 추가가 전부**여야 한다.

```ts
export type SajuProduct = {
  slug: string;
  category: "운세" | "연애" | "궁합" | "결혼·가족" | "직업·재물" | "건강·인간관계";
  title: string; subtitle: string; description: string;
  userInputPrompt: string;
  purpose: string;                        // "목적·핵심 질문"
  sections: { id: string; title: string }[];
  sajuFocus: string;                      // 기획 문서의 "사주 중점" 문단 그대로
  ziweiFocus: string;
  crossPoints: string;
  image: null | { subject: string; elements: string[] };
  needsPartner: boolean;
  adultOnly?: boolean;
};
```

`sajuFocus` 같은 걸 **파싱하지 않고 문자열 그대로 프롬프트에 꽂는다.** 문서에 쓰인 한국어가
이미 LLM이 읽을 지시문이라, 중간에 구조화하면 정보만 잃는다.

## 4. 계산 계층

새로 구현할 알고리즘은 없다. **이미 있는 라이브러리의 미사용 API를 배선하는 일**이다.

| 필요한 것 | 어디서 |
|---|---|
| 팔자·십신·공망 | `manseryeok` `calculateFourPillars` *(기존)* |
| 대운 | 같은 결과의 `luckPillars` — **gender 필수** |
| 세운·월운 | 대상 연/월의 간지를 같은 함수로 재계산 |
| 명궁·12궁 | `iztro` `astro.bySolar` *(기존)* |
| 대한·유년·**사화** | `astrolabe.horoscope(date)` / `decadalList()` |

**주의 — 화면에 나이를 나란히 찍지 말 것.** 같은 사람이라도 사주 대운은 3세, 자미두수 대한은 6세
시작으로 나온다. 서로 다른 체계라 정상인데, 붙여 놓으면 사용자는 버그로 읽는다.

## 5. 생성 파이프라인

```
결제확정 → 계산 → [1단] 골격 1회 → [2단] 섹션 순차 N회
                        └→ 이미지 (image_brief 나오는 즉시 병행)
```

### 1단 — 골격

출력 순서: `overall`(총평) → `sections[]`(요지 + **근거 배정**) → `usedMetaphors` → `image_brief`

**근거 배정이 핵심이다.** 이걸 안 하면 연애 상품의 모든 섹션이 부처궁만 쳐다본다.
1단에서 섹션마다 쓸 궁·십신을 미리 나눠준다.

| | 배정 없음 | **배정 있음** |
|---|---|---|
| 부처궁 인용 | 10/10 섹션 | **2/10** |
| 거문 | 9 | 1 |
| 등장한 궁 종류 | 3개 | **11개** |
| 원가 | 277원 | 291원 |

**품질 개선이 사실상 공짜였다.**

### 2단 — 섹션 순차

각 섹션은 골격 + **앞 섹션들이 실제로 쓴 것**(제목·첫 문장·사용한 종결어미)을 받는다.
전문을 넘기지 않아서 입력 증가가 미미하다 — 병렬(291원)보다 오히려 쌌다(296원).

| | 병렬 | **순차** |
|---|---|---|
| 해요체 유지 | 46% | **70%** |
| 최다 종결어미 비율 | 14% | 16% |
| 서로 다른 궁 | 11종 | 11종 |
| 전체 생성 | 46초 | 147초 |
| **첫 페이지까지** | 46초 | **42초** |

### 프롬프트에 반드시 박을 것 — 안 하면 망가진다

1. **`thinking: { type: "disabled" }`** — 기본값이 켜져 있다. 첫 실행에서 출력 3,000토큰 중
   **2,955가 thinking** 이라 본문이 한 글자도 안 나왔다. 모르고 붙이면 원가가 3~4배.
2. **문체를 해요체로 못 박을 것.** "앞에서 쓴 종결어미를 쓰지 마라"만 넣었더니 모델이 금지 목록을
   피하려고 **해요체를 통째로 버리고 `~한다` 문어체로 도망갔다**(해요체 0%). 어미를 기계적으로
   금지하면 문체가 무너진다. "해요체는 유지하되 그 안에서 굴려라"로 써야 한다.
3. **이미지 브리프의 대상을 명시할 것.** 안 쓰면 **내담자 본인**을 그린다. 상품은 "들어올 인연의
   예상 모습"인데 첫 실행에서 `"혼자 창가에 앉아 미소짓는 여성"` 이 나왔다.
4. **소제목에 섹션 이름을 그대로 쓰지 말 것.** 빼먹으면 `"관계 발전의 흐름: 천천히 쌓여…"` 가 나온다.
5. **일치 상태값은 지정된 5개만.** 이건 지시대로 100% 지켜졌다(위반 0건). 퍼센트도 안 만들었다.

### 프롬프트 캐시

시스템 블록(상품 정의 + 명반 근거)에 `cache_control: ephemeral`. 섹션 호출이 전부 공유한다.

> **Haiku 는 캐시가 안 걸린다.** 시스템 블록이 1,642토큰인데 Haiku 4.5 의 최소 캐시 길이는
> 2,048이다(Sonnet은 1,024). 측정된 Haiku 125원은 캐시 없는 값이다.

## 6. 전달 — 페이지와 시간

### 해결된 부분

한 섹션이 **660자**, 읽는 데 1분 안팎. 생성은 **10~14초**.
**읽는 속도가 생성 속도를 절대 못 따라잡는다.** 1페이지를 다 읽을 때쯤 2~6페이지가 쌓여 있다.

이미지도 **골격만 나오면(29초) 바로 시작**할 수 있다. 섹션 생성과 병행하면 사용자가
마지막 페이지에 도달할 때 이미 준비돼 있다. **이미지를 맨 뒤에 붙이지 말 것.**

### 미해결 ① — 0~29초 구간

총평 첫 글자는 2.1초에 나오는데 목차 완성이 28.9초. **이 28초가 빈다.** 대책 두 가지:

- **스트리밍으로 목차를 한 줄씩 채운다.** JSON 필드 순서를 `overall → sections` 로 고정하면
  순서대로 도착한다. 타로 카드 뒤집히듯 목차가 차오르는 연출이 된다.
- **골격을 둘로 쪼갠다.** 총평+요지만 먼저(짧아서 ~10초), 근거 배정은 뒤에서 조용히.
  0페이지가 29초 → 10초로 당겨진다. *미실측.*

### 미해결 ② — 누가 147초를 돌리나 (**제일 큰 기술 리스크**)

순차 생성은 전체 147초다. 이걸 **사용자 요청 하나에 붙여 두면 안 된다.** 사용자가 앱을 나가면
죽고, 함수 타임아웃에도 걸린다.

**채택안: 페이지 단위 온디맨드 + 선행 요청(prefetch).**

- 클라이언트가 `GET /pages/3` 을 부른다. 서버는 저장돼 있으면 주고, 없으면 그때 만들어 저장 후 준다.
- 각 요청이 **10~14초짜리 독립 호출**이라 타임아웃에 안전하다.
- 클라이언트는 N페이지를 읽는 동안 N+1, N+2를 미리 부른다. 버퍼 2장이면 충분하다.
- 사용자가 나가면 그냥 멈춘다. 다시 오면 저장된 데까지 보고 이어서 부른다.
- 순차 제약상 N페이지는 N-1까지 있어야 만들 수 있다. 서버가 그 선행 조건을 검사한다.

이 방식이면 **백그라운드 워커·큐 없이 끝난다.** 다만 아직 구현·검증 전이다.

### 미해결 ③ — 읽던 위치 저장

147초 동안 앱을 나갔다 오는 사람이 반드시 생긴다. 마지막으로 본 페이지 번호를 저장한다.

## 7. 저장

`users/{uid}/sajuReadings/{id}`

```
productSlug, mode(saju|ziwei|integrated), status, createdAt
birthSnapshot   구매 시점의 생년월일시·성별·자시법·진태양시 (나중에 프로필이 바뀌어도 불변)
chart           계산 결과 원본 (사주 JSON + 자미두수 JSON)
outline         총평·섹션 요지·근거 배정·usedMetaphors·image_brief
```

**계산 결과 원본(`chart`)을 반드시 같이 박는다.** 나중에 계산 로직이나 라이브러리가 바뀌어도
**그때 뽑은 판 그대로** 다시 볼 수 있어야 한다. 돈 받고 판 결과가 재접속하면 달라지는 건 사고다.

## 8. 이미지

- `1024x1536` / `low` / 158토큰 / 8초 / **8원**
- 저장 전에 **webp 재인코딩**(1024폭 q82 → 66KB). 방식은 `scripts/build-pass-art.cjs` 와 동일.
- 프롬프트에 **실존 인물 재현 금지 + 글자 삽입 금지**를 항상 붙인다(기획 문서 6.5).
- 화면에 **"명리 해석을 바탕으로 그린 예상 이미지"** 고지를 둔다.

### 다시 뽑기를 기능으로 연다

장당 8원이라 **10번 다시 뽑아도 80원**이다. 9,900원 상품에서.
실패 보상이 아니라 **셀링포인트**로 내세우는 게 낫다. 해석은 그대로고 그림만 다시 그리므로
결과의 일관성도 안 깨진다.

## 9. 실패와 환불

| 상황 | 처리 |
|---|---|
| 계산 실패 | 생성 시작 전이므로 자동 전액 환불 |
| 골격 실패 | 자동 재시도 3회 → 실패 시 자동 전액 환불 |
| 섹션 N 실패 | **그 페이지만** 조용히 재시도. 나머지는 멀쩡하다 |
| 섹션 3회 실패 | 그 페이지에 안내 + 운영자 알림. 전액 환불은 부적절(이미 읽었다) |
| 이미지 실패 | 무료 재시도. 환불 없음 (8원이라 사실상 무제한) |

전액 환불의 경계는 **"사용자가 아직 아무것도 읽지 않았는가"** 다.

## 10. 판매 제약 — 결제 전에 막아야 할 것

### 성별 필수

- 사주 **대운은 성별 없으면 계산 자체가 안 나온다**(`manseryeok` 이 gender 없으면 생략).
- 자미두수는 명궁 산출에 관여하는데, 지금 `unspecified` 를 **남성으로 때우고 있다**
  (`src/lib/ziwei/calculate.ts`).
- 타로에선 "선택안함"이 허용이었지만, **유료 사주 상품 구매 플로우에서는 필수 입력으로 막는다.**

### "시간 모름"은 자미두수·통합을 팔지 않는다

지금 `ziwei/calculate.ts` 는 시간을 모르면 **정오로 때운다.** 타로 첨부용일 땐 괜찮았지만,
시진이 틀리면 **명궁이 통째로 다른 궁으로 간다.** 리포트 전체가 다른 사람 얘기가 된다.

- **시간 모름 → 사주 모드만 판매.** 시주만 빼고 해석하면 되므로 성립한다.
- "명궁 정확도가 낮을 수 있습니다"라고 고지하고 파는 건, 환불 요구가 들어오면 지는 싸움이다.

### 섹션 수는 기획 문서와 다르다

솔로 연애는 결과 항목이 **11개**인데 제목은 "권장 10개"다. 마지막 `들어올 인연의 예상 모습` 이
이미지 섹션이다. 따라서 **텍스트 10 + 이미지 1** 로 읽는다. 이미지 섹션은 5단 구조를 갖지 않는다.
**같은 패턴이 결혼 시기·자녀에도 있다** — 상품 정의를 옮길 때 확인할 것.
