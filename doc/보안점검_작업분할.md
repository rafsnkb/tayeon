# 2026-09-19 전체 점검 — 작업 분할 목록

> 2026-09-19에 하드코딩/상수화, 미구현·임시구현, 과금·보안 허점 세 관점으로 전체 코드베이스를 점검한 결과를 실행 가능한 작업 단위로 쪼갠 문서. 이 문서를 읽는 세션/에이전트는 이 파일만 보고도 각 작업을 독립적으로 진행할 수 있어야 한다. `tayeon-a9` 세션이 컨트롤타워 역할로 배분·검증하고, 실제 구현은 다른 Claude 세션(`tayeon-fc` 등)과 Codex가 병렬로 진행한다.

**작업 시작 전 공통 규칙**
- Git 브랜치: `main`이 개발, `live`가 운영(App Hosting이 `live`를 배포). 절대 `live`에 직접 push하지 않는다. `main`에 커밋 → 사용자 확인 후 `live`로 병합.
- `admin/`은 완전히 분리된 앱이다. Tayeon 본체 라우트로 합치지 말 것.
- 수정 후 최소 `npx tsc --noEmit` 통과 확인. 로컬 dev 서버는 직접 실행하지 말 것(사용자가 확인).
- 작업 완료 시 이 문서의 해당 행 `상태`를 `완료`로 바꾸고, 무엇을 어떻게 고쳤는지 `비고`에 한 줄 남길 것. `담당` 세션 이름도 명시.

## 우선순위 1 — Critical/High (보안·과금)

### T1. [Critical] 가입/추천 보너스 무한 파밍 방지
- **담당**: `tayeon-fc`
- **관련 파일**: `src/app/api/auth/kakao/callback/route.ts` (특히 59행, 69-95행), `src/app/api/user/delete/route.ts` (13-14행), `src/lib/referral/code.ts` (`grantSignupFreePass` 59-77행, `grantSignupReferralReward` 83-117행)
- **문제**: uid가 `kakao:${카카오ID}`로 결정적이고, 가입 보너스 지급 여부 판단이 "`users/{uid}` 문서 존재 여부"뿐이다. `/api/user/delete`가 `recursiveDelete` + Firebase Auth 계정 삭제로 유저 문서를 완전히 지우므로, 같은 카카오 계정으로 탈퇴→재로그인을 반복하면 가입 무료 이용권(`SIGNUP_FREE_PASSES = 4`, `src/lib/tarot/pricing.ts:39`)이 매번 재지급된다. 추천 보상도 지급 이력이 추천인 자신의 문서 하위(`referralGrants`)에만 있어 같은 방식으로 재파밍 가능.
- **해결 방향**: 가입/추천 보너스 지급 이력을 유저 문서 트리 밖의 영구 컬렉션(예: `signupGrants/{kakaoId}`, `referralGrants/{referrerKakaoId}/{newUidOrKakaoId}` — 유저 서브컬렉션이 아닌 최상위 컬렉션)에 기록하고, 탈퇴로 삭제되지 않게 한다. 지급 전에 이 컬렉션을 먼저 확인.
- **완료 조건**: 같은 카카오 계정으로 탈퇴→재가입을 반복해도 가입/추천 보너스가 두 번째부터는 지급되지 않음을 코드로 확인(가능하면 실제 재현 또는 단위 테스트). `npx tsc --noEmit` 통과.
- **상태**: 완료 — tayeon-a9 검증 완료
- **비고**(`tayeon-fc`): 지급 이력을 users/{uid} 서브트리 밖 최상위 컬렉션으로 이전. `signupGrants/{uid}` 문서로 가입 무료 이용권 지급 여부를, `referralGrants/{referrerUid}`(+`friends/{newUid}` 서브컬렉션, `friendsInvited` 카운터)로 추천 보상 지급 여부·인원수 상한을 각각 추적해 `/api/user/delete`의 recursiveDelete로는 지워지지 않게 함. `users/{uid}.referralSignupFriends` 필드는 폐기하고 `/api/referral/me`는 `getReferralInvitedFriendsCount()`로 새 컬렉션을 읽도록 변경. `npx tsc --noEmit` 통과 확인. Firestore 보안규칙은 이미 전체 default-deny라 신규 컬렉션도 클라이언트 접근 불가(추가 규칙 불필요).
- **검증**(tayeon-a9): diff 직접 리뷰 + `src/app/api/user/delete/route.ts` 확인해 `recursiveDelete`가 `users/{uid}`만 대상이라 신규 최상위 컬렉션이 실제로 탈퇴에 안 지워짐을 재확인. `firestore.rules` 직접 열어 전체 `allow read, write: if false` default-deny 주장도 사실 확인. `npx tsc --noEmit` 재실행 통과.

### T2. [High] 리딩 API 비용 방어 — 레이트리밋 + 질문 길이 제한
- **담당**: `tayeon-fc`
- **관련 파일**: `src/app/api/tarot/reading/route.ts`
- **문제**: 동시요청 잠금(60초, `READING_LOCK_STALE_MS`)만 있고 분당/일당 횟수 제한, 질문 글자수 제한이 전혀 없다. 유효 이용권만 있으면 순차 반복 호출로 Anthropic 비용을 무제한 유발 가능.
- **해결 방향**: 후보값은 `doc/작업현황.md`의 "비용 방어" 절 참고(질문 최대 1,000자, 분당 10회·24시간당 100회 등 — 확정치 아님, 합리적 기본값으로 구현 후 조정 가능하게 상수화). UID 기준 서버 집계(Firestore 카운터 또는 유사 메커니즘)로 제한하고, 초과 시 재시도 가능 시각을 포함한 429 응답. 기존 60초 락과 공존시킬 것.
- **완료 조건**: 제한 초과 시 429 응답과 Claude 미호출·이용권 미차감을 확인. 정상 사용 시나리오(1~2회 리딩)는 영향 없음을 확인. `npx tsc --noEmit` 통과.
- **상태**: 완료 — tayeon-a9 검증 완료
- **비고**(`tayeon-fc`): `doc/작업현황.md` "비용 방어" 절 후보값(질문 1,000자, 분당 10회, 일 100회)을 상수화해 구현. 질문 길이는 요청 초입에서 400으로 즉시 거부(Claude 미호출). 분당/일당 카운터는 기존 60초 동시요청 락과 같은 트랜잭션(`acquireReadingLock`)에서 UID 기준 고정 윈도우 방식으로 증가·검사하도록 합쳐서, 두 번 왕복 없이 원자적으로 판단하고 초과 시 락도 걸지 않음(=Claude 호출·이용권 차감 전에 차단) — 재시도 가능 시각을 `retryAfterSeconds` + `Retry-After` 헤더로 429 응답에 포함. 정상 시나리오(1~2회 리딩)는 카운터가 한도 밖이라 기존 동작과 동일. `npx tsc --noEmit` 통과 확인. 실제 API 호출 재현 테스트는 로컬 dev 서버를 직접 띄우지 않는 규칙상 진행 안 함 — 사용자가 직접 확인 필요.
- **검증**(tayeon-a9): diff 직접 리뷰. 레이트리밋 걸릴 때 락/카운터를 안 건드리는지, `releaseReadingLock`이 `readingLockAt`만 지우고 분당/일당 카운터는 그대로 두는지(설계 일관성) 확인. `npx tsc --noEmit` 재실행 통과, 본체 `npm run build` 전체 통과도 확인.
